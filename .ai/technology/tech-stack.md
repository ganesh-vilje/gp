## Changelog (rev 4 → rev 5 — third internal review pass)

Three HIGH findings, nine MEDIUM, four LOW. Each is resolved by a named mechanism; nothing is
deferred to /build. The three HIGH resolutions in one line each:

| Finding | Resolution in rev 5 |
|---|---|
| **H-A** — `GET /api/session` was unauthenticated, wrote a session row per call, and sat outside every limiter, so an anonymous flood grew the `session` table and could trip the fail-closed 503 on the public path (arch F1 = sec F1) | **The anonymous CSRF token becomes stateless and the `session` table loses its anonymous rows entirely.** Unauthenticated `GET /api/session` performs **no database access at all**: it sets an `httpOnly` `__Host-csrfseed` cookie (256 random bits) if absent and returns `hmac_sha256(SECRET_KEY, seed)` in the JSON body. `user_id` on `session` becomes **NOT NULL**; a row exists only after a successful login. A flood therefore creates no rows, executes no SQL, and cannot reach the limiter or its fail-closed 503 — the failure mode is gone rather than bounded. Assertion **17** proves it (burst of 500 anonymous requests from one IP ⇒ `session` row count unchanged, public lookup still 200). The rev-4 contradiction between "created on the public lookup route's first API call" and "created by `GET /api/session`" is deleted with the mechanism it described. The tiered alternative (arch F9) is evaluated and **rejected** in `technology-comparison.md` Layer 4.3 with its reason, and **C8** now states the 3 G budget as **time-to-result including the session round trip**, which is fetched **in parallel with hydration**. |
| **H-B** — R16's mitigation ("the `httpOnly` cookie is the only place the credential is unreachable by the npm tree") did not bound the attack (sec F2) | **Restated honestly.** A malicious package on an allow-listed origin can read the CSRF token from our own JSON, then make **credentialed same-site requests with the full capability of the signed-in clerk** — every citizen name and phone the clerk may see, and **every one-time password issued while that page is open**. The `httpOnly` cookie stops credential *theft*, not credential *use*; R16 says so. Bounding controls named: the static-site CSP's **`connect-src`/`img-src`** as the exfiltration limit (with the explicit caveat that CSP does **not** stop top-level-navigation exfiltration), the **30–60 min idle window**, and **response minimisation (M-4)** — every route declares an explicit `response_model`, and the clerk **list** response carries neither `phone` nor `name`. Whether the OTP may transit the client at all is now an **explicit recorded decision** (§ Auth → *One-time password*): **yes, it must**, because FR-017/FR-018/BR-016 put account creation and password reset in the admin clerk's hands *in the application*; the operator-shell alternative is written out with the reason it was rejected. |
| **H-C** — "no `unsafe-inline`" is very likely unachievable for a Next.js 15 App Router static export (sec F3) | **Decided now, option (a): a committed post-build step** computes SHA-256 hashes of every inline `<script>` in every emitted HTML file (the App Router bootstrap and each page's `self.__next_f.push` RSC payload) and generates the static host's per-path header configuration; assertion **18** fetches the deployed preview and **fails if any `script-src` contains `unsafe-inline`** or if any page's inline script is unhashed. **Fallback (c) is recorded, not hidden:** if the spike fails, `script-src 'self' 'unsafe-inline'` is accepted as a **stated weakening** and R16's residual widens accordingly. A **spike task is recorded for /architecture** (one build, count and hash the inline scripts, prove the header file regenerates deterministically). `style-src 'self'` also blocks React inline `style` attributes, so **inline styles are forbidden in the codebase** (Biome rule + grep assertion **19**) rather than relaxed. Option (b) — Vite + React SPA, which emits no inline bootstrap — is **not** taken unilaterally: it would satisfy H4's intent but not its letter, so it stays the named fallback for C8/H-C and would be a GATE_2 question if ever chosen. |

## Changelog (rev 3 → rev 4 — human decision H3)

**The human's answer at GATE_2, verbatim:**

> **changes: use FastAPI for the backend**

This is a decision, not a question. It is **not re-litigated** anywhere in these documents: Django
vs FastAPI is closed. The recommendation is rebuilt around **FastAPI on Python 3.13**. In
`technology-comparison.md` Layer 1 the rev-3 scoring table is kept **for the record only**, with
FastAPI marked *selected by human decision H3* and scored honestly rather than re-weighted to win.

**Working assumption:** the human mentioned only the backend, so **everything else stays as in
rev 3 unless FastAPI forces a change.** Frontend rendering approach, database engine, hosting,
region, deploy model, rate-limit mechanism, PII controls, observability, cost and the AI/LLM answer
are unchanged. Below is every change FastAPI *forced*, with the reason.

| # | Forced change | Reason FastAPI forces it |
|---|---|---|
| 1 | **ORM + migrations: SQLAlchemy 2.x + Alembic** (new § ORM, migrations & data access) | FastAPI ships no ORM and no migration tool. The atomic limiter upsert and the append-only history tables need a schema authority and reviewable migrations (D6, D7, D8). |
| 2 | **Sync, not async, all the way down** — `def` endpoints, sync `Session`, sync `psycopg` | Django gave one obvious execution model. FastAPI makes it a choice, and the choice has security consequences (a blocking Argon2 hash or a `sleep` in an event loop stalls every request). At <1 rps (D1) sync is simpler and safer. |
| 3 | **Server-side session table + our own session cookie handling** | There is no `contrib.sessions`. Rev 3 requires idle timeout, browser-close expiry, logout-everywhere and revocation on password reset (sec F20, BR-016) — a stateless signed cookie cannot revoke, so the session must be a row. |
| 4 | **Password hashing via `argon2-cffi`** (new runtime dependency) | There is no `contrib.auth` hasher framework. Argon2id via a mature library is better than hand-writing a PBKDF2 hash/verify/format layer; `passlib` is unmaintained (last release 2020) and its `crypt`-based backends break on Python 3.13. |
| 5 | **Password policy is ~30 lines of our own `validate_password()`** plus Django's BSD-3-licensed common-password list, vendored with attribution | `AUTH_PASSWORD_VALIDATORS` does not exist. Min length 12 (C5), username-similarity, all-numeric and common-password checks are now ours. |
| 6 | **CSRF: synchroniser token bound to the server-side session, sent in an `X-CSRF-Token` header** (~30 lines we own) | FastAPI/Starlette ship no CSRF protection at all. Because the token is handed out in a JSON body and never in a cookie, **there is no readable CSRF cookie** — strictly better than rev 3's deliberate `CSRF_COOKIE_HTTPONLY=False` (sec F26 preference satisfied). |
| 7 | **Global deny-by-default becomes our own middleware with an explicit public allow-list** | No `LoginRequiredMiddleware` / `@login_not_required`. The allow-list is now exactly: `POST /api/lookup`, `POST /api/login`, `GET /api/session`, `GET /healthz` — and **login/session had to be added**, because Django exempted its own login view implicitly. |
| 8 | **`must_change_password` and the login limiter run in that same middleware/dependency chain, with an explicit written ordering** | Middleware order was implicit in Django's `MIDDLEWARE` list; in Starlette it must be stated or it will be wrong. |
| 9 | **Per-account backoff is a `429` + `Retry-After`, never a `sleep`** (arch F4 + sec F23) | Rev 3's "artificial delay before the credential check" occupied a request thread. With a bounded threadpool (4 tokens per worker) that is a self-DoS. The refusal is now a response, not a wait. |
| 10 | **Request validation is Pydantic models + a custom `RequestValidationError` handler returning a stable JSON error shape** | FastAPI's default 422 body is a Pydantic error list that leaks internal field paths and is awkward for a client to render; one handler maps it to `{"errors": {"<field>": "<message>"}}` so FR-020/AC-018's exact message ("Enter a valid complaint number.") is what the client displays. |
| 11 | **`manage.py check --deploy` → an in-repo `selfcheck` CLI + a settings test** | That command does not exist. The nine production invariants it used to catch are now explicit assertions. |
| 12 | **`SECURE_PROXY_SSL_HEADER`/`ALLOWED_HOSTS`/HSTS/CSP → `--proxy-headers --forwarded-allow-ips`, `TrustedHostMiddleware`, and a ~20-line header middleware** | Starlette equivalents, all asserted in tests. |
| 13 | **Management commands → two `argparse` console scripts** (`bootstrap-admin`, `unlock-account`) | No `manage.py`. Typer was considered and rejected: +2 packages to save ~20 lines. |
| 14 | **Server: gunicorn + `uvicorn-worker`** (ASGI), threadpool capped at 4 tokens per worker | `gthread` is WSGI-only. Gunicorn is kept **specifically** to retain `--timeout 30` and `--max-requests 1000`, which uvicorn's own supervisor does not provide. |
| 15 | **Static files: none served by the API at all; WhiteNoise dropped** (−1 dependency, no `collectstatic`) | H4 moves every asset to the Next.js build output on a CDN-backed static host. The API serves JSON only. |
| 16 | **Tests: pytest + `httpx`/`TestClient` + an in-repo `live_server` fixture**; `pytest-django` and `django-stubs` dropped; CI's migration dry-run becomes `alembic upgrade head` + `alembic check` | No Django test client, no `django_assert_num_queries` (replaced by a SQLAlchemy `before_cursor_execute` query-counter fixture), no `makemigrations --check`. |
| 17 | **OpenAPI docs disabled in production** (`docs_url=None, redoc_url=None, openapi_url=None`); the rev-3 `/admin/ → 404` test is **retired and replaced** by `/docs`, `/redoc`, `/openapi.json` → 404 | There is no Django admin to exclude any more, but FastAPI adds a *new* default surface that enumerates every route. Same reasoning (D5, BR-010), different URL. |
| 18 | **Python runtime dependencies rise from 4 to 8; the budget stays ≤10** | Capabilities Django bundled in one package now arrive as four (`sqlalchemy`, `alembic`, `argon2-cffi`, `uvicorn-worker`). H4 then removed `jinja2` and `python-multipart` again, so the count lands at 8 and the ≤10 cap holds without an ADR. |
| 19 | **New risks R11 (more code we own), R12 (no LTS — FastAPI/Starlette are 0.x), R13 (public lookup now needs a cookie)**; the *April 2028 Django EOL cliff* is **retired** | Direct consequences of the swap, stated in both directions. |

**What H3 gained and what it lost, honestly, in one line each.**
*Gained:* a lighter runtime (~10–20 MB less RSS per worker), end-to-end typed request/response
objects that make mypy pay for itself under D11 (`django-stubs` gone), `response_model` output

and reviewable middleware ordering, and no LTS end-of-support cliff to hand over.

security-relevant code are now ours** (R11), and a 3-year LTS security window is replaced by 0.x

## Language & backend framework — **selected by human decision H3/H4**

**Recommendation (as directed):** Python 3.13.x + **FastAPI** (current 0.11x line) on **Starlette**, one monolithic service exposing a **JSON API only**, **synchronous** request handlers, gunicorn + `uvicorn-worker` in front. Django vs FastAPI is **closed** — H3 decided it and nothing below re-argues it. What this section owns is the *consequences* of the decision and the sub-choices FastAPI leaves open.

**Sub-choice 1 — sync or async? Recommendation: sync, everywhere.** All route handlers are plain `def` (so Starlette runs them in the anyio worker threadpool), the SQLAlchemy `Session` is sync, and the driver is sync `psycopg` 3.
- *Why:* at **D1** load (<1 rps, 1–5 clerk sessions) concurrency has no value, and async buys nothing while adding a real hazard class: one accidentally blocking call — an Argon2 verify (~50–100 ms), a `time.sleep`, a sync DB call — stalls **every** in-flight request on that worker's event loop. Under sync handlers the same call blocks one threadpool token and nothing else. Given D11 (unknown team, AI-assisted implementation) the failure mode that is *hard to notice in review* is the one to design out.
- *Threadpool is capped explicitly:* `anyio.to_thread.current_default_thread_limiter().total_tokens = 4` per worker at startup. The default (40) would allow 40 concurrent Argon2 hashes and blow the 512 MB instance. **Rev 5 (arch F2) removes the rev-4 claim that "a thread never waits on a connection"** — it was false: the request pool and the limiter pool are separate, and a request that both increments the limiter and queries the database checks out two connections, so contention is possible. The correct statement is that the pools are **sized so that contention cannot exceed the plan's connection limit** (see § ORM → *Connection budget*), and that a brief pool wait at <1 rps is harmless. This is a startup line, not a comment.
- *Alternative rejected — async handlers + `asyncpg`/async SQLAlchemy:* the textbook FastAPI setup and genuinely faster under load, but it adds `greenlet`, an async session lifecycle, async test plumbing, and the blocking-call footgun above, for throughput no driver asks for (D1). Revisit only past ~50 rps.
- *Alternative rejected — mixed sync/async:* worst of both; a reviewer cannot tell at a glance which context a helper runs in.

**Sub-choice 2 — how much of Django's absence do we replace with libraries vs our own code?** Recommendation: **small, well-known libraries for anything cryptographic or schema-shaped (Argon2, SQLAlchemy, Alembic); our own ~350–450 lines for glue that is genuinely application-specific (session lifecycle, CSRF check, deny-by-default middleware, password policy, headers, two CLIs).** Never our own crypto, never our own token format beyond `secrets`/`hmac` primitives. This is the mitigation for R11 and it is the same principle rev 3 applied to the rate limiter (~60 lines over one atomic SQL statement, because the library alternative was wrong).

**Sub-choice 3 — install profile.** `fastapi`, **not** `fastapi[standard]`, and `uvicorn`, **not** `uvicorn[standard]`. The extras would pull `fastapi-cli`, `rich`, `email-validator`, `uvloop`, `httptools`, `watchfiles`, `websockets` and `python-dotenv` — none of which any requirement needs, all of which are supply-chain surface and future security bulletins (D3). Each extra we *do* want is named explicitly instead.

**Alternatives considered (for the record; the decision is the human's):** Django 5.2 LTS (rev 3's recommendation), Litestar, Flask + extensions. **Not rescored to make FastAPI win** — `technology-comparison.md` Layer 1 keeps rev 3's table and adds an honest FastAPI row that scores *below* Django on this particular requirement set, precisely because AUTH/forms/CSRF are batteries Django had and FastAPI does not. Recording that is how the trade stays visible; overriding the human is not on the table.

**Advantages (real, not consolation):** Pydantic gives declarative request validation that runs *before* the handler body, so FR-020/AC-018's "no query before validation" is structural rather than disciplined; `response_model` filters output to a declared schema, which mechanically prevents a serialiser from leaking `name`/`phone` (NFR-009, and this matters much more now that H4 makes it a JSON API — see R15); the whole stack (FastAPI, Pydantic v2, SQLAlchemy 2.x) is fully typed, so mypy earns its slot with **no stub packages**; middleware ordering is explicit code rather than a settings list; ~10–20 MB less RSS per worker than Django; no LTS end-of-support cliff to hand over.

**Disadvantages (owned):** no auth, no sessions, no CSRF, no forms, no password validators, no ORM, no migrations, no `manage.py`, no `check --deploy` — all re-derived below (R11); FastAPI/Starlette are still **0.x** and ship breaking changes in minor releases, with no LTS window (R12); a much smaller "how do I do X securely" documentation corpus than Django's for exactly the security-sensitive parts we now own; and FastAPI's defaults are API-shaped (422 JSON validation errors, OpenAPI docs exposed) so several defaults must be deliberately changed.

**Risks & mitigations:**
- *R11 — more code we own.* → Libraries for crypto/schema; every mechanism below carries a named test assertion; the security-assertions list in § Tooling is the acceptance bar.
- *R12 — no LTS, 0.x minors.* → Major/minor ceilings in `pyproject.toml` (`fastapi>=0.118,<0.120` style), monthly batched updates, a small codebase, and a test suite that exercises every middleware.
- *Team may not know FastAPI* → GATE_2 question 5 (neutral wording: is this a skills fit or a preference?).
- *Monolithic API with no service boundary* → deliberate; unchanged from rev 3.

**Long-term/maintenance:** security updates arrive as FastAPI/Starlette/Pydantic/SQLAlchemy patch releases; the 7-day target in dependency-strategy.md §4 is unchanged but now spans **four** upstreams instead of one, plus the frontend's (see § Ops ownership). No platform-specific API is used, so hosting can still move without a rewrite.

**Cost:** $0 licence (FastAPI MIT, Starlette BSD-3, Pydantic MIT, Python PSF).

## ORM, migrations & data access (new layer — forced by H3)

**Recommendation: SQLAlchemy 2.x ORM (declarative, typed `Mapped[...]` models) + Alembic, synchronous, over `psycopg[binary]` 3.**

**Alternatives considered:** (1) **SQLModel**; (2) **raw `psycopg` 3 with hand-written SQL and hand-written migration files**; (3) **Tortoise ORM / Piccolo** (async-native ORMs).

**Why recommended:** D6 and D7 remain the two requirements most likely to fail review — append-only history preserved under concurrency (BR-011/AC-014) and complaint-number uniqueness under 20 simultaneous submissions (AC-003). Those need one schema authority, real transactions, `SELECT … FOR UPDATE`, and migrations whose diffs a human can read (D6). SQLAlchemy 2.x is the only mainstream Python answer that is also **fully typed** (which is what lets `django-stubs` disappear without losing the D11 typecheck value), and Alembic is its native migration tool with an `alembic check` command that fails CI when models and migrations drift — a control Django's `makemigrations --check` gave us and which would otherwise be lost.

**Why alternatives rejected:**
- **SQLModel:** attractive on paper (one model class for table *and* schema) and it is exactly that conflation that makes it wrong here: NFR-009 requires the public API response to be a **different shape** from the table row (no `name`, no `phone`), and a library whose selling point is "the table model *is* the API model" pushes against the single most important PII control in this project (R15). Maintenance is also thinner (effectively one maintainer, versions still 0.0.x) than SQLAlchemy's, against D3. Rejected on PII shape first, maintenance second.
- **Raw `psycopg` + hand-written SQL/migrations:** viable, zero ORM abstraction, and the limiter statement is raw SQL anyway. Rejected because *everything else* — history inserts in one transaction, the edit-history rows, the session table, `alembic check`-style drift detection — becomes hand-maintained SQL with no schema authority, which is how audit tables get out of sync (D6). We would trade 2 dependencies for several hundred lines of the most boring possible code.
- **Async-native ORMs (Tortoise, Piccolo):** rejected with the sync decision above, plus far smaller ecosystems (D3, D11).

**How the two rev-3 mechanisms are expressed in this layer (both preserved exactly):**

1. **The atomic rate-limit upsert.** Unchanged as SQL, and now *physically* separated from the request session, which is a small improvement over rev 3:
   ```python
   # conceptual; exact model/DDL is /architecture's call
   stmt = (
       pg_insert(RateLimitCounter)
       .values(scope=scope, key=key, window_start=ws, count=1)
       .on_conflict_do_update(
           index_elements=["scope", "key", "window_start"],
           set_={"count": RateLimitCounter.count + 1},
       )
       .returning(RateLimitCounter.count)
   )
   ```
   executed on a **dedicated engine/connection in `AUTOCOMMIT`** (`engine.execution_options(isolation_level="AUTOCOMMIT")`), never on the request-scoped `Session`. That is the arch F3 constraint — *the increment commits independently of the request it counts* — enforced by construction rather than by remembering to nest transactions correctly. Django's `ATOMIC_REQUESTS=False` setting has no equivalent and needs none: SQLAlchemy has no request-wrapping transaction unless we write one. **Test unchanged:** a failed login, and a handler that raises, still leave the counter incremented.
2. **The append-only `complaint_status_history`, `complaint_edit_history` and `security_event` tables.** Rev 3 relied on "there is no delete endpoint" plus "`django.contrib.admin` is not installed". FastAPI/SQLAlchemy let us do better for the same cost: a `Session` event hook (`before_execute`, ~10 lines) **raises on any `UPDATE` or `DELETE` whose target is one of the append-only tables**, so the rule is enforced at the data-access layer instead of by convention. **Tests:** (a) attempting an update or delete against each append-only table raises; (b) a grep-style assertion that no `update()`/`delete()` construct in the app package names those tables. Optionally (recorded for /architecture, not required): `REVOKE UPDATE, DELETE` on those tables from the application role in an Alembic migration, if the platform permits a second role.

**Connection budget (rewritten in rev 5 — arch F2).** There are **two engines per worker**, and both are sized explicitly, because rev 4 costed only one of them:

| Engine | Sizing | Ceiling per worker |
|---|---|---|
| **Request engine** (one `Session` per request via a dependency) | `QueuePool(pool_size=4, max_overflow=2, pool_pre_ping=True, pool_recycle=1800)` | **6** |
| **Limiter engine** (`AUTOCOMMIT`, one statement, never a request `Session`) | `QueuePool(pool_size=4, max_overflow=0, pool_pre_ping=True, pool_recycle=1800)` — **`max_overflow=0` is deliberate:** the limiter must never be able to expand the connection count under exactly the load it exists to refuse | **4** |

**Total ceiling: 10 per worker ⇒ ≤20 connections at `--workers 2`**, plus one or two transient
connections for the release command and any operator `psql` session. **Verify the chosen Render
Postgres plan's connection limit at signup** (a /release checklist item): if the plan allows fewer
than ~25, drop to `--workers 1` (ample at <1 rps, D1) rather than shrinking the limiter pool.
`pool_pre_ping` is what makes a platform-side connection reset invisible instead of a 500. A
`statement_timeout` of ~10 s is set on connect (see § Hosting — it is also the replacement for one of
gunicorn's roles).

**Advantages:** one schema authority; typed models; reviewable migration diffs; `alembic check` as a CI drift gate; raw SQL available where it is the right answer (the limiter) without leaving the layer.
**Disadvantages:** SQLAlchemy 2.x's session/identity-map semantics are a genuine learning curve and its errors are less friendly than Django's; two packages where Django had zero; Alembic autogenerate needs human review (it misses some constraint changes) — which is why `alembic check` plus a reviewed diff, not autogenerate alone, is the process.
**Risks & mitigations:** *an autogenerated migration silently drops a constraint* → migrations are reviewed, `alembic check` runs in CI, and CI applies `upgrade head` from the previous revision against a real Postgres service container. *Long-lived session leaks a transaction* → one session per request via a FastAPI dependency with explicit commit/rollback in a `finally`, plus `pool_pre_ping`.
**Long-term/maintenance:** SQLAlchemy 2.x is stable and conservative (a 1.4→2.0 style break is rare and well documented); Alembic moves slowly. Both are top-20 PyPI packages.
**Cost:** $0 (SQLAlchemy MIT, Alembic MIT; `psycopg` 3 is **LGPL-3.0** — see the licence note in dependency-strategy.md §5).

## Frontend — **selected by human decision H4**

**Recommendation (as directed):** **Next.js 15** (App Router, **React 19**, **TypeScript 5.x**) on **Node 22 LTS**, built as a **fully static export** and served from a CDN-backed static host. The exact patch versions of `next`, `react`, `react-dom`, `typescript` and Node are **pinned without carets** in `package.json`/`.nvmrc` and recorded in `/plan`; `package-lock.json` is committed and `npm ci` is used everywhere. Server-rendered Jinja2 and the no-JS form-POST path from rev 3 are **withdrawn** — the human replaced them, and this document does not keep a shadow copy of the old approach.

**Rendering mode, per page — the decision that protects what is left of D4 and D5:**

| Route | Mode | Why |
|---|---|---|
| `/` public lookup | **Static (prerendered at build)** + one **client island** (`"use client"`) holding the form, the `fetch`, the `AbortController` and the result render | The HTML shell is a CDN hit with no API call and no server render, so first paint does not wait on anything; the complaint number is submitted by `fetch` and the result is rendered in place, so the number never enters a URL, a referrer or browser history (sec F11 preserved) |
| `/login` | Static shell, client island | No data to render before authentication |
| `/complaints`, `/accounts` (clerk screens) — **no dynamic segment anywhere** | **Static shell, all data fetched client-side** from the API with `credentials: "include"`; the **detail view is client state inside `/complaints`**, not a route | **Deliberately not SSR.** Server-rendering authenticated data would require forwarding the session cookie to a Node process, which would then hold citizen `name`/`phone` in its memory and potentially its logs — a second PII processor (D5, NFR-008/009) and an extra hop inside NFR-001's budget (D4) |
| ~~`/complaints/[id]`~~ | **Removed in rev 5 (arch F3 + sec F11).** No `[id]` segment is emitted | **Two independent reasons.** (1) `output: "export"` cannot build a dynamic segment without `generateStaticParams`, and there is no build-time list of complaint ids — nor may there be, since that would publish the id space. (2) sec F11 forbids the complaint number in a URL, referrer or `history` entry, and a clerk route `/complaints/<number>` would put it in all three. **Binding decision:** the clerk detail view is rendered by the non-dynamic `/complaints` route from client state (selection held in memory, no query string, no `history.pushState` carrying the number); a **committed host rewrite maps `/complaints/*` → the exported `/complaints` shell** so any stray or bookmarked deep link still loads the app instead of a 404, and lands on the list. **One Playwright spec asserts this against the exported build served with the same fallback-rewrite rule the host uses** (the E2E job serves `out/` that way — sec F9), covering `/complaints`, `/complaints/anything` and a hard reload |
| — | **No ISR, no server actions, no route handlers, no middleware, no `next/image` optimisation** | All of them require a running Node server. We do not need one, so we do not run one |

**Consequence, stated plainly: `output: "export"` means there is no Node process in production.** The frontend is a directory of HTML/JS/CSS on a CDN. Node 22 exists only on the **build** host (CI and the static host's build step). That is worth naming as a *benefit*: it removes a second production runtime that nobody was going to patch (D3), keeps the web tier at **$0** (D2), and shrinks the production attack surface to one Python service. It costs us every Next.js server feature — accepted, because the table above uses none of them.

**Client-side JS budget (NFR-001 / D4 / Conflict C8):**
- **Target: ≤120 KB gzipped first-load JS on `/`**, plus ~4–8 KB CSS. React 19 + the Next App Router runtime is a floor of roughly 90–110 KB gzipped, so the target is "the floor plus our island", not a comfortable margin.
- **Measured, not asserted, and measured early:** the route-level "First Load JS" figures printed by `next build` are checked **at /build** (a CI step can fail the build above a threshold), and the 3 s figure itself is measured on a throttled 3G profile at **/test-app** (AC-010). Rev 3 could argue analytically from ~25 KB; rev 4 cannot, and says so.
- **Payload discipline:** no CSS framework, no component library, no icon package, no `next/font` (system font stack), no client-side router prefetch on the public route, no analytics. Hand-written CSS, ~4–8 KB, one file.
- **If the measurement fails NFR-001:** the fallback is named now so nobody improvises later — (i) serve the public lookup route as a **hand-written static HTML page with ~2 KB of vanilla JS** (the rev-3 island, no React) while the clerk app stays Next.js, or (ii) accept a >3 s public page and record it as a requirement change. Both are GATE-visible decisions, not build-time improvisation.

**NFR-011 (in-flight + timeout) — now uniform, which is a genuine gain:** every one of the three core workflows goes through the same client helper: disable the control, show a spinner, `fetch` with `AbortController` and a **10 s** abort, render "The server is taking too long. Please try again." on abort or network error. Rev 3's Conflict **C6** (no in-page timeout message on the no-JS path) is **retired** — there is no no-JS path any more.

**AC-018 / FR-020 (malformed input performs no lookup) — the contract is unchanged and still server-side:** the client island does a cheap format check for UX, and the **binding** assertion is in the API — Pydantic rejects blank/whitespace/malformed complaint numbers before the handler body runs, so **no query reaches the complaint store**, asserted with the SQLAlchemy query-counter fixture (§ Tooling). The client check is explicitly *not* the contract.

**Public response shape (NFR-009, and now more important than in rev 3 — R15):** the public lookup endpoint returns an explicit **public DTO** — `{complaint_number, status, date_logged, public_update}` — declared as the route's `response_model` with `extra="forbid"`, so the ORM row cannot leak extra fields even if someone returns it directly. A test asserts that for a complaint holding both a name and a phone number, **neither string appears anywhere in the serialised response**. This is the JSON-API-shaped version of rev 3's template-discipline argument, and it is a test rather than a habit.

**Alternatives considered (for the record; the decision is the human's):**
1. **Rev 3's server-rendered templates + ~100 lines of vanilla JS** — smallest payload, worked with JS disabled, zero npm. Superseded by H4.
2. **Vite + React SPA (no Next.js)** — smaller runtime than Next.js and simpler (no framework server, no App Router semantics) but no built-in routing/prerender story; would have needed a router and a static-HTML shell anyway. A legitimate alternative *within* H4's spirit if Next.js's size becomes the blocker (see the C8 fallback).
3. **Next.js with SSR/ISR on a Node server (`next start`)** — the default way to run Next.js. **Rejected on D5/D3/D2:** it puts citizen data through a second process, adds a second production runtime to patch, and costs +$7/mo for capabilities the page table above does not use. Kept as a costed option (§ Estimated monthly cost) if the human later wants SSR.
4. **Astro / SvelteKit / plain TS + Vite** — smaller payloads than React, but H4 named Next.js.

**Why the static-export variant is recommended *within* H4:** it is the only variant that keeps citizen PII in exactly one server process (D5), keeps hosting at one paid component (D2), adds no production runtime for an unnamed ops owner to patch (D3), and gives the public page a CDN-cached HTML shell that starts painting before any API round trip (D4).

**Advantages:** a clean typed client/server contract — and in rev 5 that is a **mechanism, not a claim (arch F7)**: CI dumps the OpenAPI schema (docs remain unserved in production), **`openapi-typescript`** generates `api-types.ts`, the file is **committed**, and CI **fails if the committed types differ from a fresh generation**, so a field rename breaks CI rather than production. Uniform NFR-011 behaviour; a genuinely responsive clerk UI without full page reloads; a CDN-cached public page; the frontend cannot accidentally query the database.

**XSS posture, stated as controls rather than assumed (sec F8):** the primary control is **React's JSX escaping** — every interpolated value (clerk note, citizen name, complaint number) is escaped by construction. On top of that: **`dangerouslySetInnerHTML` is forbidden** anywhere in the frontend, and so is any inline `style` prop or `style` attribute (the CSP's `style-src 'self'` blocks them — H-C); any user-supplied `href` must pass an **explicit scheme allow-list** (`https:` and `mailto:` only — never `javascript:`/`data:`); **Biome's security and correctness rule groups are enabled explicitly** in `biome.json` (not left to defaults), and a **grep-style assertion** (security assertion 19) fails CI on `dangerouslySetInnerHTML`, `innerHTML`, `eval(`, `new Function(` or a `style=`/`style={` occurrence in the app source.
**Disadvantages:** ~5× the payload of rev 3 (C8); **requires JavaScript** (C7/R17, a requirements change); two deployables with skew potential (R14); ~350–450 npm packages where there were zero (R16); a second language and toolchain against D11; and no server-side rendering escape hatch without changing the hosting model.

**Risks & mitigations:**
- *R17 — the public page needs JS.* → GATE_2 question 8 asks the human to confirm; the analyst relaxes BR-015/AC-018/persona wording; the server-side "no query before validation" contract is retained so FR-020 does not weaken.
- *C8 — 3 s / 3G budget.* → measured at /build with a route-size gate in CI, and again at /test-app; two named fallbacks above.
- *R15 — a JSON endpoint leaks `name`/`phone`.* → explicit public DTO + `response_model` + the no-PII-in-response test; deny-by-default middleware means an unauthenticated request never reaches a clerk endpoint at all (AC-015 tested both directions **against the API**, which is the security boundary).
- *Client-side route guards are not security.* → stated explicitly: the Next.js redirect-to-login is **UX only**; every authorisation decision is the API's, and the tests target the API.
- *A stale HTML shell requests a chunk that a promotion deleted (arch F8, R14).* → three mechanisms: **promotions land outside office hours** (already R1's rule, now cited here too); the client's dynamic-import/`fetch` helper treats a **chunk-load or 404-on-asset failure as "a new version is available — reload"** and shows a reload control rather than a blank screen (a /ux item, wording defined there); and **one Playwright spec** serves an exported shell whose referenced chunk has been removed and asserts the reload prompt appears. HTML entry points already carry `no-cache` while hashed assets are immutable, which keeps the window to a single navigation.
- *Route paths, schemas and the clerk UI are public by construction (sec F5).* → under H4 the bundle ships to anyone, so `/api/...` paths, field names and every clerk screen are readable by an attacker. This is **accepted, not mitigated**: obscurity was never the control. **Authorisation is** (deny-by-default over the whole route table, assertion 14), and the `/docs` → 404 test is **hygiene, not an anti-enumeration control** — see § Auth.
- *Accessibility/CSS drift* → /ux defines the component list first; one stylesheet; test at 320 px and keyboard-only; Playwright specs run against the real exported build.

**Long-term/maintenance:** Next.js majors arrive roughly annually with real migration work, React majors less often, and both have their own security-release cadence — this is the **second patching stream** recorded in § Ops ownership and in GATE_2 question 6. `npm audit` runs in CI and Dependabot watches the `npm` ecosystem.

**Cost:** **$0** — Render Static Sites are free (build + global CDN + TLS + custom domain). A Node/SSR variant would be +$7/mo (costed option).

## Database

**Recommendation (engine unchanged by H3/H4; provider and region updated in rev 5.1 by GATE_2 answer Q1):** **PostgreSQL 17**, managed by the hosting platform — **Fly Managed Postgres, smallest plan, region `bom` (Mumbai)** *(rev 5 said Render Postgres, Singapore; that is now the rejected default — § Hosting)*. **SQLAlchemy 2.x ORM + Alembic** (§ ORM, migrations & data access) over the `psycopg[binary]` 3 driver. `DATABASE_URL` must include **`sslmode=require`**, asserted by a settings test and by the `selfcheck` startup check (sec F10). Complaint-number uniqueness enforced by a DB `UNIQUE` constraint; status-history and edit-history rows written in the same transaction as the parent update; the rate-limit counter and the new `session` table live in this database too. **Rev 4 adds one table to the rev-3 set: `session`** (server-side sessions — § Auth); it holds no PII beyond a user FK and timestamps, and it is swept deterministically like the limiter windows.

**Facts to verify at signup and record in /release (sec F10, cost F1):** encryption at rest for the instance and for platform backups; backup retention days on the chosen plan; egress allowance; region confirmation. This document assumes but does not assert them.

**Alternatives considered:**
1. **SQLite** (WAL mode) on a persistent volume, with Litestream/nightly copy for backup.
2. **MySQL 8 / MariaDB** managed.
3. **Firebase Firestore / other document store.**

**Why recommended:** D6 and D7 are the two requirements most likely to fail a reviewer: FR-013 must hold under 20 simultaneous submissions (AC-003) and BR-011 must preserve both writers' history entries. A relational DB with a real `UNIQUE` index plus `select_for_update`/serialisable semantics makes both provable with a test that actually exercises concurrency. Rev 2 adds a third reason: the atomic `INSERT … ON CONFLICT DO UPDATE … RETURNING` upsert that makes the rate limit correct (D8) is a Postgres primitive. D3 is the fourth: managed Postgres means the platform, not a nonexistent ops person, runs the daily backups — and the audit trail (D6) is the asset we cannot lose. D14 confirms the smallest plan is ample.

**Why alternatives rejected:**
- **SQLite:** technically sufficient for D1 and cheaper ($0). Rejected on D3/D6/D8: it needs a persistent volume (a Fly volume would now be possible, but a volume is a thing to size, snapshot and verify — see the note below), backup becomes a human's job to set up *and verify*, and the atomic counter would rely on a single-writer file lock. Retained as the documented fallback only if the human rejects a paid DB (Conflict C1); then Litestream-to-object-storage becomes mandatory.
- **MySQL/MariaDB:** equivalent for the audit/uniqueness requirements; `ON CONFLICT`'s equivalent (`ON DUPLICATE KEY UPDATE`) exists too. Postgres chosen on cheaper managed tiers, `RETURNING` support in the upsert (which MySQL lacks and which the limiter uses), and first-class `psycopg`/SQLAlchemy support. Preference, stated honestly.
- **Firestore/document store:** rejected outright. Multi-row transactional audit writes (D6) and a global uniqueness constraint (D7) are what document stores make awkward; per-read pricing plus lock-in fight D2/D3.

**Advantages:** correctness guarantees for the Must-priority audit, uniqueness and rate-limit requirements; platform-run backups; `psql` for the operator's occasional support query; room to grow to multi-panchayat without migration.

**Disadvantages:** a second billable component (~$6–7/mo); one more network hop than SQLite (~1 ms in-region).

**Backups (sec F8, rewritten in rev 2; made *conditional* in rev 3 per sec F18):**
- Platform daily backups are the primary mechanism; **retention to be confirmed at signup** (assumed ~7 days).
- **Off-platform copy — offered only if two preconditions are both met.** Rev 2 offered an encrypted monthly dump *and* said the control does not exist without a named key holder, which is a contradiction when GATE_2 question 6 is answered "nobody". Rev 3 resolves it: the off-platform copy exists **only if**
  - **(a)** a **named person holds the private decryption key** (recorded in /release), **and**
  - **(b)** a **named destination** exists with **its own narrowly scoped credential** (write-only/append-only where the provider supports it, usable for nothing else) and an **automatic lifecycle/expiry rule** that deletes objects older than ~90 days without anyone remembering to.
- **If either (a) or (b) is absent, there is no off-platform copy.** Platform daily backups become the *only* backup mechanism, the monthly dump is **dropped from the design and the cron is not offered** — not "offered as optional", not "manual on a checklist". An unencrypted or un-expiring dump nobody owns is a bigger risk than the shorter recoverable window it buys. The cost table marks the cron **conditional on (a) + (b)** for exactly this reason.
- **When it does exist:** a monthly `pg_dump` **encrypted before it leaves the platform shell** — `pg_dump … | age -r <recipient-public-key> > dump-YYYY-MM.age` (or GPG equivalent) — written straight to the named destination. The plaintext dump is never written to disk unencrypted and never lands on a laptop in the clear.
- **Retention:** the destination's lifecycle rule keeps the three most recent encrypted dumps (≈90 days) and expires the rest automatically; the /release checklist verifies the rule exists rather than relying on a manual **deletion step**. Rationale: these files are a full citizen-PII export (D5), so the shortest defensible window wins over "keep everything".
- **Go-live restore test:** restore one encrypted dump into a **throwaway Fly Managed Postgres instance in `bom` which is destroyed immediately afterwards** (never a dev laptop, never a shared DB), and record evidence: row counts per table, the newest complaint number present, and the destroy confirmation. Repeat at any DB major-version change.
- **Never**: production data copied into dev, CI, fixtures, or any AI tool (enforced in dependency-strategy.md §6).

**Risks & mitigations:**
- *Backup exists but was never restore-tested* → the go-live restore test above is a /release gate item with evidence.
- *Nobody performs the monthly encrypted dump* → in rev 3 this is no longer a lingering risk but a **decision rule**: without a named key holder and a lifecycle-managed destination the dump does not exist at all (sec F18). Platform daily backups continue regardless, so the accepted failure mode is "only ~7 days of history off the primary", not "no backup".
- *Free-tier databases that auto-pause (Neon/Supabase free)* → deliberately not used: a cold start threatens D4's 3 s budget.

**Long-term/maintenance:** major-version upgrades are platform-initiated and roughly annual; at this data size they take minutes. Migrations are code-reviewed and applied as the release command.

**Cost:** ~$6–7/mo (re-verify at signup; prices quoted 2026-09).

## Auth approach

**Recommendation:** an **in-repo session/authorisation layer over framework-independent primitives** — a **server-side `session` table** in Postgres, an opaque `httpOnly` cookie set by the API, **Argon2id via `argon2-cffi`**, and a deny-by-default middleware with a four-entry public allow-list. No auth SaaS, no auth framework, and **no custom crypto**.

### Session mechanism — chosen: server-side session table (not a signed cookie)

| Option | Verdict |
|---|---|
| **Opaque token in a cookie + a `session` row in Postgres** ✅ | **Chosen.** Rev 3's requirements are the deciding factor: **idle timeout**, **browser-close expiry**, **logout everywhere**, and **revocation on password reset** (sec F20, BR-016). Only server-side state can be revoked. The row also gives us a natural home for the CSRF token. |
| Starlette `SessionMiddleware` (signed cookie via `itsdangerous`) | Rejected. A signed cookie is a *bearer assertion*: once issued it is valid until it expires, so "reset this clerk's password and end their sessions" and "log out everywhere" cannot be honoured — a stolen cookie stays live for its whole lifetime. Idle timeout could only be advisory (a timestamp inside the cookie the client presents). It would save one table and ~40 lines; it cannot satisfy BR-016's reset semantics. Also avoids a dependency: **`itsdangerous` is therefore not in the stack.** |
| JWT (access + refresh) in a cookie or in `localStorage` | Rejected twice over. (a) Revocation needs a server-side denylist, which is the session table again with more moving parts and a signing-key rotation problem; (b) `localStorage` is readable by any script on the page, and after H4 there are ~400 npm packages on that page (R16) — a single malicious transitive dependency would exfiltrate every clerk credential. There are ≤6 accounts and one client; JWT solves a problem this system does not have. |

**Mechanism, precisely:**
- Cookie value = `secrets.token_urlsafe(32)` (256 bits). The database stores only its **SHA-256 hash**, so a database dump or a `psql` support query never yields a usable live session token.
- Cookie attributes: **`httpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, host-only with the `__Host-` name prefix, and no `Max-Age`/`Expires`** — the missing expiry is what makes it a browser-session cookie, i.e. rev 3's `SESSION_EXPIRE_AT_BROWSER_CLOSE=True`. (`__Host-` requires `Secure` and no `Domain`, so it is applied only when the secure-cookie flag is on; local development over `http` uses the unprefixed name. The flag is env-driven and asserted by `selfcheck`.)
- `session` row: `id`, `token_hash`, **`user_id` NOT NULL** (rev 5, H-A — there are **no anonymous rows**; a row exists only after a successful credential check), `csrf_token`, `created_at`, `last_seen_at`, `absolute_expires_at`, `revoked_at`, `user_agent_hash` (optional, no raw UA stored).
- **Idle window:** `last_seen_at` is refreshed on every authenticated request; a session with `last_seen_at` older than the configured idle window (**30–60 min**, exact figure /architecture's call within that range) is rejected and revoked. This is the direct replacement for `SESSION_SAVE_EVERY_REQUEST=True`. One small `UPDATE` per request is irrelevant at <1 rps (D1).
- **Absolute ceiling:** `absolute_expires_at = created_at + ~9 h` (one office day).
- **Rotation:** a new row is issued and the old one revoked on **login** and on **password change** (session fixation).
- **Revocation:** `revoked_at` set for *all* of a user's rows on password reset by an admin clerk, on self password change, and on "log out everywhere". A visible **logout control on every authenticated screen** remains a /ux obligation.
- **Anonymous sessions: removed entirely (rev 5 — H-A / arch F1 / sec F1).** Rev 4 created a `session` row on the first unauthenticated API call, from an **unauthenticated route that sat outside every limiter**. That is an unauthenticated write primitive: a single-source flood grows the table without bound, and because the limiter **fails closed**, the DB pressure it creates can turn the public lookup into a 503 — i.e. the CSRF mechanism could be used to take down the thing it protects. Rev 4 also described the row's origin two different ways (§ Session mechanism said "the public lookup route's first API call", § CSRF said `GET /api/session`), which is itself evidence that nobody owned the lifecycle. **Both statements and the mechanism are withdrawn.** The anonymous CSRF token is now **stateless** (below), so **no row, and no SQL of any kind, exists before authentication**. Expired *authenticated* rows are swept by the same deterministic trigger as the limiter windows (never a cron, never a 1%-probability sweep).
- **Tests:** idle expiry; absolute expiry; no-`Max-Age` (browser-close) attribute assertion; rotation on login and on password change; all sessions revoked after an admin password reset; the stored value is a hash and not the cookie value; **and (assertion 17) a burst of 500 unauthenticated `GET /api/session` + public-lookup requests from one IP leaves `SELECT count(*) FROM session` unchanged and the public lookup still returning 200** — the regression test for H-A.

### Frontend↔API topology, CORS, and where the security boundary is (H4)

- Static site: `https://<domain>.in` and `https://www.<domain>.in`. API: `https://api.<domain>.in`. **Same registrable domain**, so a `SameSite=Lax` cookie set by the API **is** sent on the site's `fetch` calls (they are cross-*origin* but same-*site*) provided the client uses `credentials: "include"`.
- **CORS is an explicit allow-list**, not a wildcard and not a regex: `allow_origins` = the two production origins (plus `http://localhost:3000` only when the dev flag is on), `allow_credentials=True`, `allow_methods=["GET","POST"]`, `allow_headers=["content-type","x-csrf-token"]`, `max_age=600`. `allow_credentials` with `allow_origins=["*"]` is invalid and is rejected by `selfcheck` at startup. **Preview/branch deployment URLs are deliberately not in the allow-list**, so a preview build cannot talk to the production API.
- **`SameSite=None` is forbidden (rev 5 — sec F6).** The whole cookie design rests on the two hosts sharing one registrable domain (A-T12). The failure case is concrete and near: **Render's default `*.onrender.com` hostnames are not the same registrable domain as each other for cookie purposes** in the way we need, and they are what exists *before* the custom domain is attached. The rule is therefore: **the custom `.in` domain must be attached to both hosts before any real citizen data is entered** (a /release gate item and new **GATE_2 question 9**). If the human cannot supply a single registrable domain, we do **not** reach for `SameSite=None` — the auth model changes to a **BFF proxy** (a paid Node service, +$7/mo, with the D5 cost recorded in § Frontend) and **returns to GATE_2** as a decision, not a patch.
- **`selfcheck` cookie/CORS invariants (extended in rev 5 — sec F6):** `httponly is True`, `secure is True`, **`samesite == "lax"`** (never `"none"`), **no `Domain` attribute is ever set**, the **`__Host-` prefix is present in production** on both the session and the CSRF-seed cookie, **every CORS origin is `https://` and inside the expected domain set** (a literal suffix check against the configured registrable domain — a typo'd or foreign origin fails startup), and **the dev flag is off**. Each is one line in `selfcheck` and one row in its test table.
- **Rejected alternative — a BFF proxy** (Next.js `rewrites` or route handlers forwarding to the API, giving same-origin and `SameSite=Strict`): genuinely attractive on CSRF grounds, and rejected because it routes **every citizen record through a second server process** that would then hold and possibly log PII (D5/NFR-008/009), requires a running Node server (+$7/mo, a second production runtime to patch — D2/D3), and adds a hop inside NFR-001's budget (D4). If the human later wants SSR, this trade reopens.
- **The API is the security boundary.** The Next.js app's redirect-to-login is **UX only**. Deny-by-default, role checks, `must_change_password` and the limiter are all enforced server-side, and AC-015 is tested **against the API** in both directions.

### CSRF — three layered controls, ~30 lines we own

FastAPI/Starlette ship **no** CSRF protection, so this is a mechanism we write. All three layers apply to **every unsafe method** (`POST`, `PUT`, `PATCH`, `DELETE`) on **every** route, with **no exemption list in the codebase at all**:
1. **`SameSite=Lax` session cookie** — a genuinely cross-site POST from an attacker page does not carry the cookie.
2. **`Origin` header check** — the request's `Origin` must be in the same allow-list as CORS; missing or mismatched ⇒ **403**. (A custom-header requirement also forces a CORS preflight, which the allow-list fails for attacker origins.)
3. **A synchroniser token echoed in `X-CSRF-Token`** and compared with `hmac.compare_digest`. **Rev 5 splits this into two paths, because rev 4's single path required a database row before authentication (H-A):**
   - **Unauthenticated (the public lookup POST) — stateless, no row, no SQL.** `GET /api/session` sets an `httpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, `__Host-csrfseed` cookie containing `secrets.token_urlsafe(32)` if one is not already present, and returns `csrf_token = base64url(hmac_sha256(SECRET_KEY, seed))` in the JSON body. On the lookup POST the server recomputes the HMAC over the cookie's seed and compares. **Verification is pure computation: no `SELECT`, no `INSERT`, no row of any kind.** Consequences, which are the point of the change: an anonymous flood cannot grow any table, cannot consume a DB connection, and therefore **cannot trip the fail-closed 503 on the public path**; there is nothing to sweep; and a valid existing seed cookie yields the same token on every call, so a repeat visitor's `GET /api/session` is idempotent by construction.
   - **Authenticated — session-bound, exactly as rev 4.** The 256-bit `csrf_token` lives in the session row, is **rotated with the session** on login and password change, and is **returned in the JSON body of the login, password-change and logout responses (arch F10)** so the client never has to guess that its token went stale after a rotation. `GET /api/session` returns it too (a read of the row the request already loaded, plus the `last_seen_at` update the session loader performs anyway).
   - **Why keep a token at all**, given `SameSite=Lax` plus the `Origin` check: the tiered alternative (Origin + SameSite only on the public POST, token only on authenticated writes) is evaluated and **rejected** in `technology-comparison.md` Layer 4.3 — the token is what forces a **CORS preflight**, which the allow-list fails for attacker origins, and it is the only one of the three layers that is a server-side *assertion* rather than a browser behaviour. It costs one extra round trip on the public route, which **C8 now measures as time-to-result** with the `GET /api/session` call issued **in parallel with hydration**, not after it.

**`CSRF_COOKIE_HTTPONLY` equivalent (sec F26): the question disappears.** Rev 3 had to leave the CSRF cookie script-readable so the page could read it. Here **no cookie carries the token** — the token travels in a JSON response body and a request header, and the only cookies are the two `httpOnly` ones (`__Host-session`, `__Host-csrfseed`). Neither is readable by page scripts.

**`SECRET_KEY` has exactly two consumers, named (sec F9):** (1) the HMAC key for the stateless anonymous CSRF token above, and (2) the salt in `h(username)` for limiter keys and `security_event` rows. Nothing else reads it, no session token is derived from it (session tokens are raw `secrets` values stored as hashes), and rotating it invalidates outstanding **anonymous CSRF seeds only** — a re-fetch of `GET /api/session` recovers, and no clerk is logged out. It therefore stays in `selfcheck` (present, ≥32 bytes) for a stated reason rather than by habit.

**Coverage and tests (both directions, one module):**
- **403 without a valid token on (a) an authenticated write endpoint and (b) the public lookup POST.** The public, unauthenticated endpoint is **not** exempt: without this control an attacker could drive complaint-number guessing through unwitting visitors' browsers and spread it across *their* IP addresses, defeating the per-IP limiter (D8/BR-010). That is a concrete reason, not a ritual.
- 403 when `Origin` is absent or not in the allow-list, on the same two endpoints.
- **A token minted from a different `SECRET_KEY`, and a token replayed with a different seed cookie, are both rejected** (the stateless path's equivalent of "not another user's token").
- **The login, password-change and logout responses each carry the rotated `csrf_token`**, and the pre-rotation token is rejected immediately afterwards (arch F10).
- **Assertion 17 (H-A):** a burst of unauthenticated requests from one IP leaves the `session` table row count unchanged and the public lookup serving 200s.
- A grep-style assertion that **no exemption decorator or exempt-path list exists** in the app package.
- A test that the CSRF middleware is registered **before** the router and **after** the session loader (ordering is code now, so it is asserted).

### Middleware order — explicit, because Starlette makes it ours to get wrong

Outermost → innermost: **(0)** uvicorn `--proxy-headers` (not middleware) → **(1)** `TrustedHostMiddleware` → **(2)** security-headers middleware → **(3)** CORS → **(4)** session loader (cookie → `session` row, idle/absolute checks, `request.state.user`) → **(5)** CSRF → **(6)** deny-by-default authorisation + `must_change_password` → **(7)** router/dependencies. Stated here so /architecture implements it and a test asserts the registered order.

### Deny-by-default authorisation and the public allow-list

- Middleware **(6)** rejects every request that is not authenticated with **401** (or a redirect hint for the client) unless its path+method is in the **explicit public allow-list**, which is exactly: `POST /api/lookup`, `POST /api/login`, `GET /api/session`, `GET /healthz`. Everything else — including any route added later — is closed by default. This replaces Django's `LoginRequiredMiddleware`; note that `POST /api/login` and `GET /api/session` had to be **added** to the list because Django exempted its own login view implicitly.
- **Role check:** a `require_admin_clerk` FastAPI dependency on the two account-management endpoints, so a regular clerk hitting the URL directly is denied **403** (FR-019, AC-017 bullet 3). `is_admin_clerk` is the **only** elevation; there is no staff/superuser concept to leak.
- **AC-015 is tested in both directions:** anonymous is denied on every clerk endpoint (parametrised over the route table, so a new route is covered automatically) and allowed on exactly the four allow-listed ones.
- **OpenAPI docs are disabled in production** — `FastAPI(docs_url=None, redoc_url=None, openapi_url=None)` unless the dev flag is on, asserted by a test that **`/docs`, `/redoc` and `/openapi.json` all return 404**. **Rev 5 states its value honestly (sec F5):** under H4 the **route paths, the request/response schemas and the entire clerk UI are public by construction** — they are compiled into a bundle that anyone can download. So this test is **hygiene** (one less interactive surface, one less thing to leave on in production, and it removes a live "try it" client pointed at production), **not an anti-enumeration control**, and rev 4's inherited "no unnecessary surface enumerating every route and schema" framing overstated it. **Authorisation is the control**: deny-by-default over the whole route table (assertion 14) plus `require_admin_clerk`, both of which hold whether or not the attacker knows the paths. The schema is still generated *in CI* — and now consumed by `openapi-typescript` to produce the committed client types (arch F7); it is simply never served.
- **Every route declares an explicit `response_model` — binding, and asserted (sec F4).** Rev 4 relied on this for the *public* endpoint only (R15). It is now the constraint for **every** route, because after H-B the realistic attacker is a malicious npm package running with the clerk's own session: whatever a clerk endpoint returns, it returns to that attacker. The mechanism: a **route-table-parametrised test** iterates `app.routes` and fails on any route whose `response_model` is `None` (a new endpoint is covered the day it is added, not the day someone remembers), and each response schema is `extra="forbid"`. **Response minimisation with it:** the clerk **list** response carries `complaint_number`, `status`, `date_logged` and a truncated subject only — **no `phone` and no `name`** — and those move to the **detail** response, which is fetched one record at a time (FR-016 already describes the detail view as where full information lives). A compromised page can therefore still read any single record the clerk opens, but it cannot vacuum the whole citizen contact list from one list call, and the idle window bounds how long it has. That is a real reduction, stated without pretending it is a fix.

### Password hashing — chosen: `argon2-cffi` (Argon2id)

| Option | Verdict |
|---|---|
| **`argon2-cffi`, Argon2id, `m=9216 KiB, t=4, p=1`** ✅ | **Chosen.** MIT, maintained by Hynek Schlawack, a top-tier PyPI package, and the same library Django's own Argon2 backend uses. Gives `hash()`, `verify()` and `check_needs_rehash()` plus a self-describing encoded hash string — so **we write no hash format, no salt handling and no constant-time comparison of our own** (the R11 mitigation in action). |
| Stdlib `hashlib.pbkdf2_hmac` (600k iterations, SHA-256) | Rejected, narrowly. Zero dependencies and OWASP-acceptable — this is what rev 3 used via Django. Rejected because *without* Django we would own the encoded-hash format, the salt generation, the upgrade-on-login path and the constant-time compare: ~30 lines of crypto-adjacent code we would rather not own than one mature dependency. Kept as the documented fallback if `argon2-cffi`'s C extension ever causes a build problem on the platform. |
| `passlib[bcrypt]` | **Rejected on maintenance.** Last release **1.7.4, October 2020**; the project is effectively unmaintained, and its `crypt`-based backends target a stdlib module **removed in Python 3.13** (PEP 594) — exactly our interpreter. Checked 2026-09. Recorded in dependency-strategy.md §7. |
| `pwdlib[argon2]` | Rejected. A thin, young wrapper (0.x, small maintainer base) over `argon2-cffi`, which we can use directly. One fewer layer, one fewer thing to patch (D3). |

**Memory arithmetic, because Argon2 is memory-hard and the instance is 512 MB (arch F7 discipline):** `m=9216 KiB` is ~9 MiB per concurrent hash. The threadpool is capped at 4 tokens per worker, so the worst case is 2 workers × 4 = **8 concurrent hashes ≈ 72 MB transient**, on top of ~240–300 MB steady (§ Hosting) ⇒ peak ≈ **376 MB**, leaving ~136 MB. The OWASP-recommended `m=19456 KiB` (19 MiB) would peak at ~450 MB and is therefore **rejected on this instance size**, with the reason recorded rather than the parameters silently weakened; `m=9216, t=4, p=1` is itself an OWASP-listed configuration. If the instance is ever upsized, raise `m` first. Login is a rare operation (≤6 accounts, D1) and the login limiter bounds attempts, so the transient peak is a burst bound, not a steady state.

### Password policy — ~30 lines we own (`AUTH_PASSWORD_VALIDATORS` is gone)

`validate_password(password, *, username)` returns a list of failures and is called from both account creation and password change:
- **minimum length 12** (Conflict **C5** — BR-016's floor is 8, so 12 satisfies it but is stricter; still flagged, not silently applied);
- **not similar to the username** (casefold containment plus a cheap ratio check);
- **not entirely numeric**;
- **not in a common-password list** — Django provided a 20k list, so we **vendor Django's own BSD-3-licensed `common-passwords.txt.gz`** (~10k entries) into the repo with attribution and the licence recorded in dependency-strategy.md §5 as a *vendored asset*, not a dependency. If the human prefers no vendored data file, the check is dropped and that is stated rather than quietly missing.
- **Tests:** one per rule, plus a test that the 60-bit generated one-time password (below) passes all of them.

**Login protection (sec F7 / arch F7; reworked in rev 3 by sec F16 + arch F4):** three counters over the same table, but with an **evaluation order** and a **key-shape rule** that rev 2 left unsaid.

**Evaluation order is part of the control (sec F16) — evaluate cheapest and least attacker-influenced first:**
1. **Per source IP first.** Key `login:ip:<derived_ip>`; threshold **100 failures / 15 min** (deliberately generous — 1–5 clerks share one office IP). This key contains **no attacker-supplied data**. If this ceiling is exceeded, **short-circuit and reject immediately, before any username-keyed row is written.** That is what stops an attacker from creating one table row per invented username.
2. **username+IP** — key `login:userip:<h(username)>|<derived_ip>`; **20 failures / 15 min**. The **primary blocking decision**.
3. **Per account** — key `login:user:<h(username)>`; **a delay, not a lock** (see arch F4 below).

**Key-shape rule (sec F16):** the username component is **never stored raw or variable-length**. It is normalised (casefold, strip) and then **hashed and truncated to a fixed-width digest** — e.g. the first 16 hex characters of a SHA-256 of `(username || a settings-held salt)`. Consequences: bounded row width regardless of a 10 KB submitted username; no username enumeration from the limiter table; no PII-ish identifier sitting in an operational table (D5). Collisions at 64 bits across ≤6 real accounts are irrelevant, and a collision can only make a limit *slightly stricter*, never looser.

**Deterministic cleanup (sec F16) — the 1% probability is withdrawn.** Rev 2's "delete old windows on ~1% of requests" is probabilistic: it can skip cleanup arbitrarily long and it puts an unbounded `DELETE` on a random citizen's request. Rev 3 requires a **deterministic trigger**, /architecture to choose one of:
- delete rows older than two windows **on window rollover** for the key being touched (i.e. when the upsert creates a *new* `window_start` for that key, sweep that key's older rows), or
- an exact counted trigger (every Nth limiter call, N from settings) with a **`LIMIT`-bounded** delete.
Either way the delete is bounded in rows touched and never blocks the request path for long.

**Required test (sec F16):** a burst of **many distinct usernames from one IP** must (a) be rejected by the per-IP ceiling **without writing a username-keyed row per attempt**, (b) leave the counter table bounded (assert a row-count ceiling after the burst), and (c) leave the **public lookup still serving 200s** — it must not tip the fail-closed 503 path. This is the test that proves the short-circuit ordering actually exists in the code.

**Anti-lockout rule for the per-account counter (arch F4) — chosen and stated:** with ≤6 accounts, a hard per-account lock is a **self-DoS**: anyone who knows a clerk's username can lock the office out, and every documented unlock path except the operator shell *requires a working login by another clerk*. So:
- The per-account counter applies a **progressive backoff, never a hard lock**, and — **new in rev 4 (arch F4 + sec F23)** — the backoff is expressed as an **immediate refusal, not a wait**: the API returns **`429 Too Many Requests` with a `Retry-After: <1|3|5>` header** and the generic message, and **no request thread ever sleeps**. Rev 3's "small artificial delay before the credential check" would occupy one of only **4 threadpool tokens per worker** (§ Language & backend framework); eight concurrent delayed logins would stall the public lookup, turning an anti-brute-force control into a self-DoS. The client island renders the retry hint; the attacker gains nothing, because the credential check does not run until the window elapses.
- The refusal window is capped at ~5 s so it never approaches the 10 s client abort or gunicorn's 30 s timeout.
- The backoff is **skipped entirely for an IP that has a recent successful login for that account** (e.g. within the last 24 h, recorded per account+IP). A clerk at the office desk that logged in this morning is never delayed by an attacker elsewhere.
- **Test (updated):** the third consecutive failure for account X from attacker IP A returns **429 with `Retry-After`**, and the assertion explicitly checks that the response is fast (no `sleep`), while a login for X from office IP B (recent success) returns 200 with no `Retry-After`.
- **Blocking** — an actual refusal to check credentials — is carried **only** by **username+IP** (step 2) and the **per-IP ceiling** (step 1). Both are scoped to the attacker's own IP, so a remote attacker can never block the office.
Successful login clears the username+IP and per-account counters **for that IP**; the per-IP ceiling is not cleared by a success (a success among 100 failures is what credential stuffing looks like). **Unlock path (ties to Q-015):** (a) wait out the window — now the normal case, because nothing is hard-locked; (b) another admin clerk resets the password, which clears counters; (c) the operator runs the **`unlock-account <username>` console script** on a one-off platform shell. All three documented in /release.

**Counter durability (arch F3) — same rule, cleaner mechanism:** the limiter upsert **commits independently of the request it is counting**. In rev 4 that is structural rather than disciplinary: the statement executes on a **dedicated engine in `AUTOCOMMIT`**, not on the request-scoped `Session` (§ ORM, migrations & data access), so there is no request transaction that could roll it back. Django's `ATOMIC_REQUESTS=False` has no equivalent and needs none — SQLAlchemy wraps nothing around a request unless we write it. **Test unchanged:** a **failed** login (and a handler that raises) still leaves the counter incremented.

**May the one-time password transit the client at all? — explicit decision (rev 5, H-B).** The question is real: BR-016 has the API return a freshly issued password **in a JSON body**, which page JavaScript then renders, so under H-B's threat model (a malicious npm package inside the clerk's own page) **every OTP issued while that page is open is capturable**. The alternative was considered: *issue passwords only from the operator's one-off platform shell*, so no OTP ever reaches a browser. **Decision: the OTP does transit the client, and the reasons are requirement-level, not convenience:**
- **FR-017/FR-018/BR-013/BR-016 put account creation and password reset in the admin clerk's hands, inside the application.** Moving them to a shell would make every new clerk and every forgotten password an **operator** task — and D3 says the Operator is explicitly a *one-time bootstrap actor*, not an ongoing role. The feature would exist on paper and be unusable in the panchayat office.
- The shell path also has **no audit trail in `security_event`** and no `must_change_password` enforcement unless we duplicate that logic in a CLI, i.e. it trades a browser exposure for a weaker control surface.
- **`unlock-account`/`bootstrap-admin` already cover the break-glass cases** from the shell, so the shell-only variant adds no capability we lack.
**Residual, recorded rather than argued away:** an attacker who owns the page owns every OTP issued during that session, and an OTP is a live credential for up to 72 h. Bounding controls: **single-use + 72 h expiry + forced change**, **all sessions revoked when it is issued**, `no-store`, the OTP is **never** persisted client-side (no `localStorage`, no URL, no query string), the CSP's `connect-src` limits where it can be sent (H-C), and the **idle window** limits the exposure period. This residual is folded into **R16**. If the human wants it removed instead, the shell-only variant is the named alternative and it costs FR-018's in-app reset — a GATE_2-shaped trade, not ours to take silently.

**One-time password issued by an admin clerk (BR-016, sec F7/F12):** generated with `secrets.choice` over a 32-character unambiguous alphabet (no `0/O/1/l/I`), **12 characters ⇒ 60 bits of entropy** — well above any guessing concern for a value that lives for hours. It is:
- returned **exactly once**, in the JSON response to the create-account / reset-password call, on a response carrying `Cache-Control: no-store, no-cache, must-revalidate` and `Referrer-Policy: no-referrer`; it is **never** retrievable again by any endpoint, and the client displays it without persisting it (no `localStorage`, no URL, no query string);
- **single-use and expiring after 72 h** (`password_issued_at` + `must_change_password`); after expiry the clerk cannot use it and the admin must reset again;
- never logged (not in application logs, not in `security_event`, not in access logs), never emailed;
- accompanied by **revocation of every existing session for that user** (§ Session mechanism).
- **Test:** the value appears in exactly one response body, is absent from a second fetch of the same account, and never appears in captured log records or `security_event` rows.

**Forced change enforcement (sec F12):** `must_change_password` is enforced in **middleware (6)**, which rejects every authenticated request with **`403` + `{"must_change_password": true}`** except the change-password endpoint, logout and `GET /api/session` — not only at login, so a bookmarked deep link or a direct API call cannot bypass it. The client uses that flag to route the user to the change-password screen; the **enforcement is server-side**, the redirect is cosmetic. Tested with a direct API call to a clerk endpoint while the flag is set.

**Failed-login logging (sec F7):** log `username`, derived client IP, timestamp and outcome at WARNING; **never the submitted password**, and never a "user does not exist" distinction in the response (AC-001 bullet 2 generic message). A test asserts the submitted password string never appears in captured log records. **Rev 3 (sec F19):** stdout logging alone is not durable enough now that Sentry is gone — the same events are also written to the append-only **`security_event` table** (§ Observability), which lives inside the platform's daily backups.

**FR-015/AC-019 bootstrap (sec F4; now a console script, not a management command):** **`bootstrap-admin`** is a `[project.scripts]` entry point built on **stdlib `argparse`** and is **interactive by default**: it prompts for username and password on stdin (`getpass`, no echo) when run on a one-off platform shell, so **no standing admin credential exists in the environment**. It is idempotent (clear no-op if an admin clerk already exists). It **refuses to run when `sys.stdin.isatty()` is false** unless `--from-env` is passed explicitly.

**Why `argparse`, not Typer (item 7 decision):** two commands, ~40 lines of argument handling between them. Typer would add `typer` + `click` (2 packages, plus `rich` if the extras leak in) to save perhaps 20 lines of `add_argument` calls — a bad trade against the dependency budget and D3 (every package is a future security bulletin nobody is assigned to read). Recorded so /architecture does not add it for convenience.
- The env-var path (`--from-env`) exists only for a genuinely non-interactive platform. It **refuses to run without the explicit `--from-env` flag**, and when used it (a) forces `must_change_password=True` on the created account, and (b) prints a reminder that the variable must be deleted.
- If the env path is used, /release **must** carry two evidenced checklist items: the bootstrapped admin has `must_change_password=True`, and `BOOTSTRAP_ADMIN_PASSWORD` has been deleted from the platform environment (screenshot or `env`-listing evidence).
- No credential is ever written to a repo file, a data migration, or a fixture.

**Alternatives considered:** (1) Hosted identity SaaS — Auth0 / Clerk / Firebase Auth; (2) Supabase Auth; (3) OAuth / "Sign in with Google" for clerks.

**Why recommended:** D9 is unusually specific and actively hostile to SaaS auth. BR-016 requires the admin clerk to *see the new password once on screen* and hand it over verbally, because no email or SMS channel exists (D10). FR-019 requires a role check that also blocks direct URL access — one FastAPI dependency. With ≤6 accounts (A12), per-MAU pricing is pure cost against D2. Mature libraries for hashing; **never custom crypto**; everything else is a session row and a middleware chain whose order is asserted by a test.

**Why alternatives rejected:**
- **Auth0/Clerk/Firebase Auth:** cannot express BR-016's on-screen one-time password without a hack; add an external dependency and a network hop on every login; add per-MAU cost and a third-party PII processor (D5); and FR-019's authorisation logic stays in our code anyway.
- **Supabase Auth:** same email-centric mismatch, plus a second platform whose free tier pauses.
- **OAuth/Google:** clerks are not assumed to hold personal Google accounts on a shared office computer, and NFR-003 specifies "at minimum, username + password".

**Advantages:** exact fit to FR-017–FR-019 and BR-016; no external calls in the login path; testable end-to-end offline (AC-001, AC-015, AC-017); the session token is in an `httpOnly` cookie, so the npm dependency tree cannot **exfiltrate a reusable credential** — **but rev 5 does not claim more than that (H-B):** the tree can still *use* the cookie from the page. See R16 for the accurate statement of what is and is not bounded.

**Disadvantages:** no MFA by default (optional TOTP costed below); no self-service reset (deliberate, A10); **we own session lifecycle, CSRF, deny-by-default and password policy** — ~350–450 lines rather than rev 3's ~60 (R11, R2).

**Optional, costed for the human (sec F14):** TOTP second factor for the **admin clerk only** — `pyotp` (MIT, mainstream, +1 runtime dependency, ~0.5–1 day of work now that there is no `django-otp` to lean on, $0/mo), using any free authenticator app; the recovery story is the operator's one-off shell. Not adopted by default because no requirement asks for it and it adds a lockout mode to an office with one admin. Offered, not assumed. (Rev 3 offered `django-otp`; that package is Django-only and is retired from this document.)

**Risks & mitigations:**
- *Admin self-lockout* (Q-015) → BR-013 recommends a second admin clerk; three unlock paths above; `bootstrap-admin` doubles as break-glass.
- *Passwords relayed verbally/on paper per BR-016* → outside our control; mitigated by 72 h expiry, single use, forced change and session revocation. Flagged (C2), not overridden.
- *Session/cookie/CORS misconfiguration* → the `selfcheck` startup check plus explicit tests for cookie attributes, the CORS allow-list, the middleware order and the five security headers (sec F13). This is the replacement for `check --deploy` and it is enumerated in § Tooling.
- *We wrote the session layer* (R11) → every bullet in § Session mechanism has a named test; no custom crypto; token generation is `secrets`, comparison is `hmac.compare_digest`.

**Long-term/maintenance:** nothing to renew. The two-role model is a boolean column; a real permission table is a later migration if multi-panchayat arrives.

**Cost:** $0.

## Rate limiting (rewritten — arch F1, sec F1, sec F2, arch F11)

**Rev 1 was wrong and is withdrawn.** `django-ratelimit` over Django's `DatabaseCache` fails for two independent reasons: `BaseCache.incr` is a non-atomic get-then-set, so parallel requests lose increments; and `DatabaseCache` culls entries at `MAX_ENTRIES=300`, so an attacker rotating keys can evict their own counter. That is the same class of defect for which rev 1 rejected `LocMemCache`.

**Recommendation: an in-repo fixed-window limiter over an explicit Postgres counter table.** No new dependency (`django-ratelimit` is dropped), no new service.

```
-- conceptual; exact model/DDL is /architecture's call
rate_limit_counter(scope text, key text, window_start timestamptz, count int,
                   PRIMARY KEY (scope, key, window_start))
```
Each check is **one statement**:
`INSERT INTO rate_limit_counter (scope, key, window_start, count) VALUES (%s,%s,%s,1) ON CONFLICT (scope, key, window_start) DO UPDATE SET count = rate_limit_counter.count + 1 RETURNING count;`
Atomic under any number of workers, threads or connections; no read-modify-write; no eviction policy to defeat. Thresholds live in environment settings so Q-013 can change without a code change. **Rev 4:** written as SQLAlchemy's `pg_insert(...).on_conflict_do_update(...).returning(...)` — the same statement, type-checked, with the exact construct shown in § ORM, migrations & data access.

**Transaction rule (arch F3) — unchanged rule, structural mechanism:** this statement executes on a **dedicated engine/connection in `AUTOCOMMIT`**, never on the request-scoped `Session`, so it **commits independently of the request being counted** by construction rather than by convention. There is no request-wrapping transaction in SQLAlchemy to nest inside (Django's `ATOMIC_REQUESTS` has no equivalent and needs none). A counter that a rolled-back request can undo is not a rate limit. Tested (see § Auth).

**Cleanup — deterministic, not probabilistic (sec F16).** Rev 2's "delete rows older than 2 windows on ~1% of requests" is withdrawn: a probability can skip cleanup indefinitely and dumps an unbounded `DELETE` on a random citizen's request. Rev 3 requires a **deterministic trigger** — a bounded, `LIMIT`ed delete of that key's stale rows **on window rollover** for the key being touched, or an exact "every Nth call" counter with N in settings. Still no cron and no job runner (D10). A row-count ceiling after a burst of distinct keys is asserted in a test (§ Auth, sec F16).

**Client-IP derivation — exact rule (sec F2):**
1. Trust **only** the platform's forwarded header (`X-Forwarded-For` as set by Render's proxy); `REMOTE_ADDR` behind that proxy is the proxy itself and must not be used as the client identity.
2. Take the **right-most entry that is not a trusted-proxy address** — i.e. strip the known platform proxy hop(s) from the right, then use the next value. Never the left-most (client-controlled) entry.
3. The platform proxy addresses/behaviour are recorded explicitly in settings as `TRUSTED_PROXY_HOPS` (Render is expected to be **1**; confirm against Render's documentation at /architecture) — a number, not a guess spread through the code. **Rev 3 (sec F17): the value must be *verified*, not assumed, in three ways** —
   - **Startup check:** the in-repo **`selfcheck`** routine (run both as an app startup hook and as a standalone CLI in CI — the replacement for `manage.py check --deploy`) **refuses to start** if `TRUSTED_PROXY_HOPS` is not **explicitly set** in the environment. No implicit default: a silent `1` on a platform with two hops turns the whole limiter into an attacker-controlled key, and that must not be a quiet condition.
   - **Positive unit test:** feed a **realistic multi-hop header** (`X-Forwarded-For: <real client>, <upstream proxy>, <platform proxy>` shaped to the configured hop count) and assert the derived key equals the **real client address** — not just the rev-2 negative tests, which pass even against an implementation that returns a constant.
   - **/release verification step:** from a **known source address**, make one request to the live deployment and confirm the derived key equals that address — via a single temporary log line (derived key only, no headers, no complaint number), evidence captured, **then the log line is removed** and the removal is a checklist item. This is the only way to catch a wrong hop count on the real platform.
4. Normalise before keying: IPv4 as-is; **IPv6 truncated to its /64 prefix**, so an attacker with a routed /64 cannot rotate addresses to get unlimited attempts.
5. If the header is missing or unparseable, treat the request as **one shared bucket** (`"unknown"`) rather than as unlimited — fail closed, not open.
6. **Rev 4 — the explicit Starlette/uvicorn equivalents of rev 3's Django settings** (all of them test assertions, not intentions):
   - **`uvicorn --proxy-headers --forwarded-allow-ips=<value>`** replaces `SECURE_PROXY_SSL_HEADER`. It makes `request.url.scheme` and any redirect correct behind the platform's TLS terminator. `--forwarded-allow-ips` is set to the platform proxy's address/CIDR **if Render documents one**; otherwise to `*` **with the reason recorded** — the container receives traffic only from the platform edge — and with the compensating note that we do **not** use uvicorn's parsed client address for the limiter: the limiter uses our own five-step rule and `TRUSTED_PROXY_HOPS`, which we own and test. Verified on the live deployment at /release (step 3 above).
   - **`TrustedHostMiddleware(allowed_hosts=[...])`** replaces `ALLOWED_HOSTS`, pinned to the real hostnames; `selfcheck` fails if it is empty or contains `*` in production.
   - **HTTPS:** we rely on the platform edge's HTTP→HTTPS redirect plus **HSTS** (`max-age=31536000; includeSubDomains`, no `preload`) rather than adding Starlette's `HTTPSRedirectMiddleware`, because a redirect middleware combined with a misconfigured `--proxy-headers` produces a redirect loop that is invisible in tests. **/release verifies** with one `curl http://<domain>` that the edge returns a 301; if it does not, `HTTPSRedirectMiddleware` is added and the loop risk is retested.
   - **Cookies** are set explicitly on the response (`httponly=True, secure=True, samesite="lax"`, no `max_age`, `__Host-` prefix when secure) — see § Auth. `selfcheck` fails if the secure-cookie flag is off in production.
   - **CORS** is the explicit allow-list in § Auth; `selfcheck` fails on `allow_origins=["*"]` together with `allow_credentials=True`.
   - Rev 1's `USE_X_FORWARDED_HOST` error stays withdrawn; it has no equivalent here.

**Required tests (all in the unit/integration suite):**
- **AC-011 under parallel load:** fire >20 *concurrent* requests (`concurrent.futures` against a live-server fixture, real Postgres) from one IP and assert exactly the allowed number succeed and the remainder are throttled. A sequential loop is **not** acceptable evidence for AC-011.
- **Positive IP derivation (sec F17):** a realistic multi-hop `X-Forwarded-For` at the configured hop count derives the **real client address**.
- Spoofed `X-Forwarded-For` (attacker prepends fake addresses) does not change the derived key.
- IPv6 rotation within one /64 shares a bucket.
- Missing/garbage header → the shared `"unknown"` bucket, not a bypass.
- Threshold is read from settings (config-change, not code-change).
- **Counter survives a rolled-back request** (arch F3) and **a failed login still increments** (§ Auth).
- **Key-burst containment** (sec F16): many distinct usernames from one IP → per-IP short-circuit, bounded row count, public lookup unaffected.

**DB-failure behaviour (arch F6):** the limiter **fails closed**. If the counter write raises, the public lookup endpoint returns **`503` with a stable JSON error code**, and the client island renders the friendly message ("The service is temporarily unavailable — please try again in a few minutes") — the *wording* moved to the frontend, the *behaviour* is unchanged and asserted on the API. No lookup is performed. This costs nothing in availability terms because the lookup itself needs the same database. Login behaves identically. `/healthz` **does** execute `SELECT 1` with a short statement timeout and returns 503 on failure, so the uptime pinger detects a DB outage (the outage that actually matters) and not just a live process; it returns a bare `ok`/`unavailable` with no version or dependency detail. **New in rev 4:** because the static frontend is served from a CDN and not by the API, the public page still *loads* during a full API outage and shows the error state instead of a platform error page — a small genuine gain from H4.

**Alternatives considered and rejected:**
1. **A single worker with an in-process counter** (evaluated as the simplest option). At <1 rps one worker is ample and it removes the cross-*process* problem. **Rejected as the mechanism** because a dict-plus-lock counter is still per-process, and it makes a security control depend on a server flag that anyone can change in a dashboard. A limiter that breaks when someone types `--workers 2` is not a control. (The worker count is still chosen conservatively — see § Hosting.)
2. **Managed Redis / Valkey** (Render Key Value smallest paid tier, ~$10/mo at 2026-09 pricing; Upstash free tier with per-command limits). Technically the textbook answer: `INCR` is atomic and cheap. **Rejected on D2/D3** — it is a third billable component (+~70% on the hosting bill) and a third thing to patch/monitor, for a counter that one Postgres statement handles at this volume. Revisit only if load grows past ~50 rps, which no driver predicts.
3. **An off-the-shelf ASGI limiter** (`slowapi`, `fastapi-limiter`). `slowapi` wraps `limits` and defaults to in-memory storage (per-worker, wrong) or Redis (option 2); `fastapi-limiter` **requires** Redis. Both are small-maintainer 0.x packages that would own a security control (D3, and dependency-strategy.md §1's maintenance bar). **Rejected** for the same reason `django-ratelimit` was rejected in rev 2: the dependency's correctness depends on a backend we do not have. This is the FastAPI-ecosystem equivalent of that finding, checked rather than assumed.
4. **Cloudflare free edge rate-limit rule** — good *additional* layer, free, but it moves a Must-verifiable behaviour (AC-011) outside the application and the test suite. Welcome later as defence in depth.

**Advantages:** atomic and correct regardless of worker/thread/connection count; no eviction to defeat; no extra service or dependency; fully testable in CI against real Postgres; thresholds are config.

**Disadvantages:** ~60 lines of code we own and must test (accepted — the alternative is a wrong control or a paid service); one small write per public lookup (irrelevant at D1); limiter state shares the application database.
- **Fixed windows allow up to 2× the threshold across a boundary (arch F8).** 20 requests in the last second of one minute plus 20 in the first second of the next is 40 in ~2 seconds while never exceeding 20 *per window*. **Accepted at pilot load:** the driver (D8/Q-013) is "stop bulk guessing", and 40 attempts in 2 seconds against a ≥40-bit non-sequential complaint number (sec F11) achieves nothing. If it ever matters, a **sliding window** (two adjacent window rows, weighted by elapsed fraction) is a **code-only change with no schema change** — the `(scope, key, window_start)` table already stores what it needs. Recorded so /architecture does not re-litigate it.

**Risks & mitigations:**
- *Village NAT / CGNAT means many citizens share one public IP*, so 20/min could throttle legitimate kiosk users. **Still the most likely real-world complaint.** Mitigation: fail *soft in wording* ("too many attempts, try again in a minute" — never a CAPTCHA or a hard block, per Q-013), log throttle events, keep the threshold in config, and surface this to the human as input to Q-013 (question 4).
- *Counter table growth* → **deterministic** deletion of old windows (sec F16), a fixed-width hashed key component, the per-IP short-circuit that stops one-row-per-invented-username, and a tiny row size; at D1 the table stays in the low thousands of rows, and a test asserts a row-count ceiling after a key burst.
- *Rate limiting is only half the anti-enumeration story* → see the complaint-number floor below.

**Complaint-number security floor for /architecture (sec F11):** the format is the architect's call, but it must meet: **≥40 bits of random component** (e.g. 8 characters of Crockford base32 from `secrets`), **non-sequential** (no inference from one number to the next), plus **one checksum character** so typos fail format validation before any lookup (BR-015/AC-018) and dictionary sweeps waste attempts. Additionally: the public lookup is a **POST** (number never in a URL, referrer or browser history), the response carries `Cache-Control: no-store` and `Referrer-Policy: no-referrer`, and complaint numbers are **excluded from application logs**. Without this floor, the rate limit is the only defence against enumeration (A-T7) — which is not enough.

**Security headers (sec F13) — now in two places, because there are two deployables:**
- **API (~20-line Starlette middleware, no dependency):** on every response — `Strict-Transport-Security: max-age=31536000; includeSubDomains`, `Referrer-Policy: no-referrer`, `Permissions-Policy: geolocation=(), camera=(), microphone=()`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Cache-Control: no-store` on every authenticated and every lookup response, and `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; base-uri 'none'` (an API returns JSON; it needs nothing).
- **Static site (host header rules, committed as configuration):** `Content-Security-Policy: default-src 'self'; connect-src 'self' https://api.<domain>.in; img-src 'self' data:; style-src 'self'; script-src 'self' 'sha256-…' …; frame-ancestors 'none'; base-uri 'none'; form-action 'none'` — `connect-src` must name the API origin, which is a **new requirement created by H4** (rev 3's `default-src 'self'` sufficed when everything was one origin), plus the same `Referrer-Policy`, `Permissions-Policy`, `nosniff` and `X-Frame-Options`.
- **`unsafe-inline`: decided in rev 5, not deferred to /build (H-C / sec F3).** Rev 4's "Next.js's static export can be built without inline scripts" was optimistic and probably wrong: the App Router's prerender emits an **inline bootstrap** plus **per-page inline `self.__next_f.push(...)` RSC payload scripts** whose contents change with every build, there is **no Node process to mint a nonce**, and the static host's headers are **per-path**. The decision:
  - **(a) Chosen — a committed post-build hashing step.** `npm run build` is followed by a small in-repo script (~40 lines, no dependency) that parses every emitted HTML file, computes the **SHA-256 hash of each inline `<script>`**, and writes the host's header configuration with a per-path `script-src 'self' 'sha256-…'` list. It runs in CI and on the static host's build, so a page whose inline script changes regenerates its own hash. **Assertion 18** fetches the deployed preview and **fails if any returned `script-src` contains `unsafe-inline`, or if any inline script in the served HTML has no matching hash in the served header** — placed immediately beside assertion 3.
  - **A spike task is recorded for /architecture:** one real `next build`, count the inline scripts per page, confirm the hash set is deterministic for a fixed input, and confirm the static host accepts per-path headers of that size. If the spike fails, take (c).
  - **(c) Recorded fallback, not hidden:** accept `script-src 'self' 'unsafe-inline'` as a **stated weakening**, with R16 restated (an injected inline script becomes possible, so CSP stops being an exfiltration bound for script execution and only `connect-src` remains) and the weakening named in the ADR.
  - **(b) Not taken unilaterally:** a **Vite + React SPA** emits no inline bootstrap and would make `script-src 'self'` trivially true. It satisfies H4's *intent* ("a separate frontend") but not its *letter* ("Next.js"), so it is **not** chosen here; it remains the named fallback for **C8** and, if ever preferred, becomes a GATE_2 question rather than an evaluator decision.
  - **`style-src 'self'` blocks React inline `style` attributes too.** We do not relax it: **inline styles are forbidden in the codebase** (all styling is the single hand-written stylesheet), enforced by Biome plus the grep assertion in **assertion 19**. If a genuine need appears, the narrow escape is `style-src-attr 'unsafe-inline'` with the reason recorded — never a blanket `style-src 'unsafe-inline'`.
- **Tests:** the API headers are asserted on a public and an authenticated response in pytest; the static-site headers, **the generated hash set** and the absence of `unsafe-inline` are asserted by a Playwright/HTTP check against the deployed preview in the E2E suite, because host configuration cannot be unit-tested. All are listed in the security-assertions list (3, 18, 19).

**Cost:** $0.

## PII controls (new section — sec F3)

D5 plus the resolved Q-001 create one exposure this stack must name rather than assume away.

**The problem:** Q-001 resolved that the public page shows complaint number, status, date logged **and the latest note** (FR-009). The note is clerk-authored free text. That is an unstructured PII channel on an unauthenticated page: a clerk writing "spoke to Ramesh on 98xxxxxxxx, will fix Tuesday" publishes exactly what BR-005/NFR-009 forbid, and no amount of template discipline prevents it.

**Stack-level decision — DECIDED BY THE HUMAN AT GATE_2 (Q7: "option (b), fixed status messages"), binding on /architecture:** the public page renders **enumerated status messages selected from a fixed list — no clerk free text of any kind**. This is the fully PII-proof option, and it is the one the human chose over (a). Recorded for the record: **(a) a distinct public-safe `public_update` field** the clerk fills deliberately (still depends on clerk behaviour, so a control rather than a guarantee) — **rejected by the human**; and **(a′) publishing the clerk's internal note as-is** — never offered, since it is the defect this section exists to remove. The internal free-text note remains **clerk-only**, and a test asserts the public response body contains no citizen name or phone value for a record that has both.

**Consequences recorded honestly:**
- ~~This is a GATE_2 question for the human (question 7)~~ — **ANSWERED: option (b), 2026-09-09.** This **resolves Q-016** and narrows the resolved Q-001 answer; **the requirements-analyst is amending FR-009 and BR-005** to say "one of a fixed set of status messages" instead of "latest note".
- **NFR-008/NFR-009 coverage moves from *partial* to *full once the enumerated `public_update` field exists in /architecture*** — the coherence table row is updated to say exactly that. The remaining step is mechanical (define the enumeration and the `response_model` field, then the leak test becomes claimable); there is no open question behind it any more.
- The honest note about (a) still stands as the reason (b) is better, and the human agreed: **(b) is a technical guarantee; (a) would have been a discipline.**

**Other PII controls in this stack:** no government-ID field (BR-009); **no third-party origin on the public page at runtime** — every npm package is *bundled at build time* and served from our own origin, there is no CDN-hosted script, no web font, no analytics and no tag manager, and the CSP's `connect-src` names only our API (the trust shift is to build time, and that is what R16 and `npm audit` cover); **no third-party error tracker at launch** (see § Observability); **the public API response is an explicit DTO with no citizen fields, asserted by a test** (R15 — the JSON-API-shaped replacement for rev 3's template-discipline argument); **no SSR of authenticated data, so no second process ever holds citizen PII** (§ Frontend); encrypted, short-retention backups with a named key holder (§ Database); production data never copied to dev/CI/AI tools (dependency-strategy.md §6); complaint numbers and PII excluded from logs; `no-store` on public and credential-bearing responses.

## Background jobs

**Recommendation:** **None.** No Celery, no RQ, no task queue of any kind, no cron service in the MVP. (Rev 5 removes "Solid Queue" from this sentence — a Rails-only product, and a rev-1 leftover: arch F4.)

**Cost:** $0 (or ~$1/mo if the encrypted dump is automated).

**Server choice — gunicorn + `uvicorn-worker`, and why not uvicorn alone (item 8):**
| Option | Verdict |
|---|---|
| **`gunicorn` + `uvicorn_worker.UvicornWorker`, 2 workers** ✅ | **Chosen.** Keeps the two rev-3 mechanisms that reviewers accepted and that uvicorn's own supervisor does not provide: **`--timeout 30`** (a wedged worker is killed rather than hanging until the platform notices) and **`--max-requests 1000 --max-requests-jitter 100`** (worker recycling bounds any slow leak on a 512 MB instance). Costs **+1 runtime dependency**: since uvicorn 0.30 the gunicorn worker class lives in the separate **`uvicorn-worker`** package (MIT, maintained by the uvicorn/encode team) — the in-tree `uvicorn.workers.UvicornWorker` is deprecated. | `uvicorn --workers 2` alone | Rejected, narrowly. −2 dependencies (`gunicorn`, `uvicorn-worker`) and uvicorn has had a multiprocess supervisor since 0.30, but it offers **no per-request timeout and no max-requests recycling**. Replacing them would cost an in-app `anyio.fail_after` timeout middleware plus a DB `statement_timeout` plus an accepted unbounded-leak risk — more of our own code (R11) to save two mature packages. Kept as the fallback if `uvicorn-worker` is ever abandoned. |
| Hypercorn / Granian | Rejected: no advantage here, smaller ecosystems, and Granian is young (D3, dependency-strategy.md §1's maintenance bar). |

Note honestly: with an ASGI worker, gunicorn's `--timeout` kills the **whole worker** (all of its in-flight requests), not just the slow one. At 2 workers and <1 rps that is an acceptable blunt instrument, and a **`statement_timeout` of ~10 s** on every DB connection (§ ORM) means the common cause — a slow query — is caught first and returns a normal 503.

**Memory arithmetic against the 512 MB instance (recomputed for rev 4 — arch F7 discipline; rev 5.1: the instance is now a Fly `shared-cpu-1x` machine with 512 MB, so the arithmetic is unchanged and so is the conclusion):** a FastAPI + SQLAlchemy + psycopg worker with this app's surface sits at roughly **80–120 MB RSS** (~10–20 MB lighter than the Django worker); 2 workers ⇒ **~160–240 MB** steady. The anyio threadpool adds stack space: **2 × 4 = 8 threads × ~8 MB ≈ 64 MB** at worst ⇒ **≈ 240–304 MB**, leaving **≈ 208 MB**. **Plus the Argon2 transient:** up to 8 concurrent hashes × 9 MiB ≈ **72 MB** during a login burst ⇒ **peak ≈ 376 MB, headroom ≈ 136 MB** (§ Auth explains why `m=9216` and not OWASP's 19 MiB). Steady-state margin ~41%, burst margin ~27%; **4 workers remains out of the question**, and a free memory alert at ~420 MB is worth setting. Serving no static files (§ File storage) removes rev 3's file-serving buffers from this budget. If memory pressure appears: drop to `--workers 1` with 8 threadpool tokens (ample at <1 rps) — no security consequence. **To be measured at /test-app, not trusted:** these are estimates, and rev 3's own arithmetic was wrong once already.

**Timeout coherence with NFR-011:** gunicorn's 30 s timeout is the backstop against a wedged worker, the DB `statement_timeout` (~10 s) catches slow queries, and the **user-visible** timeout is the 10 s client-side `AbortController` in the Next.js island (§ Frontend) — so NFR-011's message comes from our own UI on all three workflows, never from a platform error page.

**Deploy model — ONE model, written once (arch F5, sec F9):**
1. **Auto-deploy is OFF on *both* deployables** — the Fly API **and** the Render static site. Pushing to `main` deploys nothing. **There is no GitHub→Fly deploy automation of any kind:** no `flyctl` deploy action, and **no Fly deploy token in CI** (consistent with "no deploy credential lives in CI", sec F9). Render static sites default to auto-deploy on; turning it off is an explicit /release checklist item, because "it's only a frontend" is exactly how an unreviewed production change happens.
2. CI runs on every push/PR and must be green for **both** stacks (Python and frontend jobs).
3. **A human promotes a specific commit, twice.** The two candidate mechanisms were considered and **one is picked, as required: the human runs `fly deploy` from a local checkout of the reviewed, CI-green commit** (`fly deploy --build-arg …` against the digest-pinned Dockerfile), then promotes the static site from the Render dashboard. *Rejected alternative:* CI builds and pushes the image to `registry.fly.io` and the human promotes it with `fly deploy --image <digest>` — attractive because the artefact would then be exactly what CI tested, but it requires a **registry-push token in CI**, which is the credential we deliberately do not have. If /release later wants the CI-built-image model, it is a deliberate change with that trade written down. Either way the deploy is **human-triggered**, which satisfies CLAUDE.md ("no production deploy — the human does those") and R1's "deploy outside office hours".
4. **Order matters (R14):** promote the **API first**, then the static site, and only ever ship **additive** API changes (a new field is fine; a renamed or removed field is a two-step deploy). The static bundle in a citizen's browser cache can be one version behind for minutes, so the API must remain compatible with the previous frontend. Rollback order is the reverse.
5. `alembic upgrade head` runs as the **`release_command` in `fly.toml`** — Fly runs it on the new image before traffic shifts and **aborts the deploy if it fails**.
6. **Rollback** = `fly releases` / `fly deploy --image <previous digest>` for the API (Fly keeps prior releases addressable) and "redeploy previous build" for the static site (see the additive-migration and additive-API rules).
7. **Post-deploy smoke check:** one Playwright E2E spec (login → log a complaint → public lookup) is run against production by the human after both promotions, and the result is the /release evidence that the two deployables actually match.
8. `main` is **protected**, and rev 4 states the rule **once**, folding in the rev-3 advisories arch F3 / sec F25: **require a pull request before merging (no direct pushes) + green required checks + linear history + no force-push + no deletion — and *no* required human review.** Rev 2 asked for both a required review *and* Dependabot security auto-merge; those are mutually exclusive, because a bot cannot satisfy a required human review. Option (b) is taken and **now paired with "require a PR"**, which costs the bot nothing (Dependabot opens PRs anyway) but stops an unreviewed direct push to `main` — the gap option (b) alone left open. Rationale for no required review: a 1–5-person pilot with an unknown implementing team and no named ops owner (D3, D11) cannot guarantee a second reviewer on demand, and CI (Ruff, mypy, pytest on real Postgres, `alembic check`, `pip-audit`, `selfcheck`, Biome, `tsc`, Vitest, `next build`, `npm audit`) plus a **human promotion step for every production deploy** are the real gates. **Two-eyes survives where it earns its keep:** a *new dependency addition in either ecosystem* still needs a second pair of eyes (dependency-strategy.md §6). **Auto-merge is narrowed (sec F25):** Dependabot may auto-merge **only patch/minor version bumps of packages already present in `uv.lock`/`package-lock.json`** — never a package that is new to the lockfile, never a major. Rev 1's "deploy on push to `main`" remains withdrawn as contradicting CLAUDE.md.

**CI hardening (sec F9):** every third-party GitHub Action is **pinned by full commit SHA** (not a tag); each workflow declares `permissions: contents: read` at workflow level and raises it only per-job where genuinely required; `pull_request_target` is not used and **no secrets are exposed to fork-PR workflows**; the deploy step is not automated at all (point 1), so no deploy credential lives in CI.

**Environments / staging (arch F5):** **there is no staging environment at launch.** Compensating controls, stated instead of implied:
- CI runs the full suite **and `alembic upgrade head` from the previous revision against a Postgres service container**, plus `alembic check` for model/migration drift, so a broken migration fails before promotion.
- **New in rev 4:** the static host's **PR preview builds are free**, so every frontend change *does* get a real deployed environment to look at before promotion — the frontend half of the missing staging environment comes for nothing. Preview origins are deliberately **not** in the API's CORS allow-list, so a preview talks to no production data; a preview is a UI review tool, not a functional environment. This is a genuine, if partial, improvement on rev 3.
- Migrations are **additive-only / forward-compatible** (append-only history tables per D6, no hard delete per BR-008): no column drops or renames in the same deploy as the code that stops using them. This is what makes rollback-by-redeploy safe.
- **Rollback = promote the previous build**; the DB is left forward-compatible.
- **Costed option for the human:** a second Fly Machine + the smallest Postgres for staging ≈ **+$10–14/mo** (roughly doubling the bill, and it would exceed the approved ≤$16 envelope, so it is a GATE decision rather than an add-on). Recommended *only* if the human wants a rehearsal environment; for a 6-screen pilot the three controls above are proportionate.

**Secrets:** `SECRET_KEY`, `DATABASE_URL` (with `sslmode=require`) and threshold overrides are set with **`fly secrets set`** for the API — never in the repo, never in `fly.toml`, never in CI — and in the Render static site's build settings for the one public value the frontend needs (`NEXT_PUBLIC_API_BASE_URL`, public by construction). No bootstrap credential is stored at all under the interactive default (§ Auth).

- *Billing account and domain renewal* → **Owner: the human (GATE_2 Q3: "I own hosting, card and domain")**; a lapsed card or domain still silently kills the pilot, so it is a /release handover item, but it is no longer unassigned.

- **Security patches are merged but never deployed (arch F1).** This is the most important line in this section. Auto-merge keeps `main` current; **production keeps running the vulnerable version indefinitely**, because promotion is a human dashboard click and no human is assigned to it. The repository, the lockfile, Dependabot and CI will all show green while production is unpatched. Do **not** read "dependencies auto-update" as "production is patched" in /release or in the ADR.
- Auto-merged Dependabot security PRs keep the Python dependencies current in the repository **only while CI stays green and the platform stays unchanged**; a failing auto-merge sits unread indefinitely.
- A high/critical CVE with no automatic fix stays unpatched past the 7-day target, **in either ecosystem**. The SLA becomes aspirational; do not claim it in /release.
- **The frontend drifts faster than the backend.** Next.js/React majors and the ~350–450-package npm tree age quicker than a Python service does; within ~18 months an unmaintained frontend is the likeliest source of a known-vulnerable dependency (R16). Recommend recording "who upgrades Next.js" as a dated handover item to the panchayat/state IT contact even if no individual is named — this is the rev-4 replacement for rev 3's April 2028 Django item.
- **Two promotions, not one.** A security merge that touches the frontend needs its own promotion; a human who remembers the API and forgets the static site leaves the vulnerable bundle live on the CDN.
- Backups continue (platform-run) but are never restore-tested again after go-live, and the encrypted off-platform copy **is never offered at all** (sec F18 — no key holder means no dump); the recoverable window is the platform's retention (~7 days).
- Uptime alerts go to a mailbox nobody reads, so NFR-007's evidence trail exists but is unobserved.
**~~Recommendation to the human~~ — SATISFIED (rev 5.1).** The recommendation was "even 1 hour per quarter, assigned to a named person". Q6 assigns it to **the human**, at the ~1.5–2 h/quarter this document costed. The residual recommendation is narrower and stays open for /release: **name the encrypted-dump destination** and **name a backup person** (or the state IT contact) so the single owner is not a single point of failure.

**Tests — recommendation, three layers:**

4. Spoofed-XFF, IPv6-/64-rotation and missing-header limiter cases, **plus the positive multi-hop XFF derivation** (sec F17).
5. No password in log records, and **the one-time password appears in exactly one response body and in no log or `security_event` row**.

9. **A burst of distinct usernames from one IP short-circuits on the per-IP ceiling, leaves the counter table bounded and does not 503 the public lookup** (sec F16).
10. **Anti-lockout:** the attacker IP receives **`429` with `Retry-After` quickly (no thread sleep — sec F23)** while the office IP with a recent success logs in normally (arch F4).

14. **Deny-by-default:** parametrised over the whole route table — anonymous is denied on every route except the four allow-listed ones (AC-015, both directions, against the API).
15. **`must_change_password`** blocks a direct API call to a clerk endpoint while the flag is set (sec F12).
16. **Middleware registration order** equals the order stated in § Auth.
17. **(New — H-A / arch F1 / sec F1) Anonymous-flood containment:** a burst of ~500 unauthenticated `GET /api/session` and public-lookup requests from one IP leaves `SELECT count(*) FROM session` **unchanged** (the stateless path writes nothing) and leaves the public lookup **returning 200, not 503**. Paired with a unit test that the anonymous CSRF path performs **zero SQL statements** (the query-counter fixture asserts an empty statement list).

**AC-018 verification restated (arch F9, adjusted for rev 4):** the contract is **not** "no network request", and it is **not** "zero queries" either — the session/CSRF middleware legitimately reads the `session` table and the limiter legitimately increments before validation runs. The precise assertion is:
1. **Server-side (primary):** for blank, whitespace-only and format-invalid input, **no statement touching the `complaint` table executes** — asserted by the query-counter fixture **by table name, not by count** — and the response carries exactly "Enter a valid complaint number." (BR-015) via the `RequestValidationError` handler. Pydantic makes this structural: the handler body never runs.
2. **Client-side (secondary):** Playwright asserts the exact message appears in the island.

**Lint & format — recommendation: Ruff (Python) + Biome (frontend).**

Monthly scheduled run re-audits **both** ecosystems against current advisory databases. Dependabot enabled for **`pip`/`uv` and `npm`**, with security PRs auto-merging on green CI **only for patch/minor bumps of packages already present in the lockfiles** (§ Hosting point 8, sec F25). ## Observability (rewritten — sec F6)

**Recommendation: no Sentry at launch.** Application logs to stdout, captured and retained by the platform, plus a **free uptime pinger** (UptimeRobot / Better Stack free) hitting `/healthz` every 5 minutes with alerts to a shared office address — the concrete mechanism NFR-007 asked architecture to define — **plus, new in rev 3, a durable `security_event` table.**

**Security event log — stack-level decision (sec F19).** Dropping Sentry (a rev-2 fix) left every security-relevant event living **only** in platform stdout logs whose retention is short (days) and unconfirmed. For a system whose central asset is an audit trail (D6) that is not good enough: "was there a brute-force attempt last month?" would be unanswerable. Rev 3 therefore records **one small append-only table in the existing Postgres** — **zero new dependencies, zero new services, zero new cost, and inside the platform's daily backups**:

| Aspect | Decision |
|---|---|
| Table | `security_event`, append-only (no update, no delete path in the application), same database, same migrations |
| Events persisted | login **success**, login **failure**, admin password reset (issued), account creation, and **throttle events** (public-lookup and login limiter trips) |
| Columns | event type, actor (the `user` FK or the submitted username in **hashed** form for a failure — same `h(username)` shape the limiter uses, sec F16), **derived** client IP (the five-step rule, IPv6 already /64-normalised), timestamp, and a short outcome/reason code |
| Never stored | **the submitted or issued password (in any form)**, and **the complaint number** (sec F11 keeps it out of every log). No free text, no request body, no headers |
| Retention | Grows at a few rows per day at D1 — trivial. Trimming is a later decision, not an MVP job; NFR-010 forbids no automatic deletion of *complaints*, and this table holds none |
| Verified by | A test asserting rows are written for login success/failure and that no row contains the password or a complaint number (added to the security-assertions list) |

This is deliberately **not** a logging framework, not an APM, and not a second audit system: it is one table, written from the same code paths that already log to stdout. It is listed in the coherence table as NFR-007/audit evidence alongside the pinger, because it is what makes a post-incident question answerable at all now that no error tracker exists.

**Why this, and not the hardened Sentry the finding also allowed:** the two options scored a near-tie in rev 1 (52 vs 49) — a margin made entirely of an optimistic PII score. Re-scored honestly in rev 2 the order flips to **53 vs 46** (technology-comparison.md Layer 10), and both drivers point the same way. **D5:** Sentry is the *only* remaining third-party processor of citizen data in the stack; even with `send_default_pii=False`, `include_local_variables=False`, `max_request_body_size="never"`, a `before_send` deny-list and a pinned data region, the residual risk is a framework internal that captures a variable we did not anticipate — and the compensating test (raise a real exception from a populated complaint form and assert the serialised event contains none of the synthetic values) proves it only for the paths we thought to test. **D3:** it is also an account, a DSN, a quota and a data-region setting that nobody owns after launch. Removing it deletes a dependency, a config surface, a PII path and an unowned account. What we lose is proactive notification of a 500 on a page the pinger does not hit; at 1–5 clerks in one office, a broken page is reported by phone within minutes, and the platform log search finds the traceback.

**Pre-approved recipe if GATE_2 question 6 names an ops owner** (adopt then, not now): `sentry-sdk` with `send_default_pii=False`, **`include_local_variables=False`**, **`max_request_body_size="never"`**, an explicit `before_send` **deny-list** for `name`/`phone`/`description`/`password`/complaint number, **data region pinned at signup**, `traces_sample_rate=0`, plus the compensating test above (populated form → real exception → assert the serialised event contains none of the synthetic values, not merely that the fields are absent). Adding it is $0 and ~2 hours.

**Alternatives considered:** Sentry free tier as recommended in rev 1 — withdrawn, see above; a self-hosted Grafana/Loki/Prometheus stack — rejected outright, it would cost more than the entire application (D2) and needs an owner (D3).

**Risks & mitigations:**
- *A 500 goes unnoticed until a clerk phones* → mitigation: `/healthz` covers process-and-DB availability; gunicorn access/error logs go to platform log search; if the office reports "it broke earlier", the logs are there. Accept under D13 (office-hours 99%, not 24/7).
- *Platform log retention is short (typically days)* → mitigation: **security-relevant events are no longer only in stdout** — they are rows in `security_event`, inside the platform's daily backups (sec F19). Tracebacks and access logs remain stdout-only, which is sufficient for same-day diagnosis at a pilot; confirm the retention figure at signup and record it.
- *Uptime alerts reach nobody* → this is the D3 gap; see § Ops ownership.

**Cost:** $0.

## AI/LLM decision

**Decision: NO. This product does not use AI or an LLM anywhere in the MVP.** (Unchanged in rev 2; no finding challenged it.)

Reasons, tied to requirements:
1. **No requirement needs it.** All 20 FRs are deterministic CRUD, validation, role checks and exact-match retrieval. **BR-004 explicitly forbids** partial matches, wildcard search and "did you mean" suggestions on the public lookup — the one place a language model might be argued for is ruled out by a business rule. FR-007's search/filter is by status and exact number.
2. **Categorisation is out of scope.** Q-008's accepted default is free-text description only, no category or SLA field; categorisation and routing sit in Future scope.
3. **It fights the cost driver.** Any inference adds per-request or per-month cost against NFR-006, for a system whose entire hosting budget is ~$14/mo.
4. **It fights the latency driver.** NFR-001's 3 s / 3G budget has no room for an inference hop on the public path.
5. **It fights the privacy driver.** NFR-008/NFR-009 and BR-005/BR-009 keep citizen name, phone and complaint text tightly held. Sending complaint text to a third-party model is a new PII processor and a new leak path with no business need — and rev 2 has just *removed* the last such processor (Sentry) for exactly this reason.
6. **No ops capacity for it.** D3: nobody owns prompt regressions, model deprecations or provider outages.

**No AI SDK, no vector database, no embedding pipeline, and no "AI-powered" feature flag will be added** (also a hard "out" in dependency-strategy.md §7). Production data is never pasted into an AI tool (dependency-strategy.md §6).

**When to revisit (and only then):** if the human pulls **complaint categorisation/routing** or **multi-language support (Q-004)** out of Future scope. Even then, the first candidates are a fixed category dropdown and **frontend i18n with human translations** (`next-intl` or `react-i18next` — the H4-era equivalent of what rev 3 got from Django's built-in i18n; +1 npm dependency, inside the § budget) — cheaper, deterministic and testable than any model. **Rev 4 note:** H4 slightly *raises* the bar for adding a language, because translation strings now ship in the client bundle and Conflict C8 already makes that bundle contested.

## Conflicts

- **C1 — NFR-006 ("low-cost") vs D3/D6 (no ops owner + a Must audit trail).** The cheapest option (~$5–6/mo VPS) transfers OS patching and backup *verification* to a human the requirements do not name. The recommended ~$14–15/mo buys away the most severe failure mode. **Recommendation: accept ~$14–15/mo.** If the human prefers the cheaper path, a named person must own patching and monthly restore tests, recorded in the ADR.
- **C2 — BR-016 (password shown once on screen, relayed verbally) vs conventional credential handling.** With no email/SMS channel (D10) this is a reasonable pilot compromise and the human's decision; it is why no auth SaaS fits (D9). **Not overridden.** Mitigated by 72 h expiry, single use and forced change.
- **C3 — AC-018 ("no lookup is performed" for malformed input) vs a client-side-only implementation.** **Restated in rev 5 (arch F4):** resolved **server-side** — Pydantic rejects blank/whitespace/malformed input before the handler body runs, so no statement touching the `complaint` table executes (asserted by table name, § Tooling); the client-side format check is a **UX nicety and explicitly not the contract**. Rev 4 still ended this entry with "Rules out an SPA (D12)", which is a rev-3 sentence that H4 made false: we now *are* an SPA-shaped client. The no-JS half of D12 is **superseded by H4 and escalated in C7**; the validation half survives intact and is stronger than before.
- **C4 — Q-013's 20/IP/min default vs shared-IP reality (R3). RESOLVED at GATE_2 (Q4: "keep 20/min").** The trade-off was put to the human with the NAT caveat and the 60/min alternative; the human kept 20. **The threshold is confirmed at 20 lookups/IP/minute**, stays **config-driven** so it can be raised without a code change, and R3 is now an accepted risk rather than an open one. No override; nothing left to decide here.
- **C5 — our `validate_password()` minimum length 12 vs BR-016's stated minimum of 8** (new in rev 2; rev 5 fixes the title, which still named Django's `AUTH_PASSWORD_VALIDATORS` — arch F4). BR-016 sets a *floor* ("at least 8"), so 12 does not violate it, but it is stricter than the analyst's default and will reject 8–11-character passwords an admin clerk might choose. **Recommendation: keep 12** — these are shared-office accounts with an audit trail behind them, and the password is machine-generated at issue anyway (60 bits). Flagged for the requirements analyst/human rather than applied silently; drop to 8 on request, one settings line.
