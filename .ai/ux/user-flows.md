# User Flows

Six flows cover all 17 user stories (see ux-decisions.md traceability table). Each lists trigger, steps, success, and every failure path with its recovery.

## Flow 1 — Clerk authentication (US-001)
**Trigger:** clerk opens `/login`, or is redirected there from any authenticated route (no session / expired session).

1. Enter username + password → submit. Client checks only "both fields non-empty" before submit (server is the authority).
2. **Success, `must_change_password=false`:** redirect to `/complaints` (or the originally requested route).
3. **Success, `must_change_password=true`:** redirect to `/change-password`; every other route is blocked (server 403 + `must_change_password:true`) until resolved. On that screen: enter new password (≥12 chars, live length counter) twice → submit → success returns to `/complaints`.
4. **Failure — wrong username or password (401):** generic message **"Incorrect username or password."** — never states which field was wrong or whether the account exists. Password field clears and receives focus; error announced via `aria-live`.
5. **Failure — rate-limited (429):** message **"Too many attempts. Please wait {n}s and try again."** using the `Retry-After` header; submit button disabled with a live countdown, no page reload needed. A recent successful login from the same office network is not delayed (server-side; transparent to the UI).
6. **Failure — network/timeout (10 s abort):** **"The server is taking too long. Please try again."**; form values kept, button re-enabled.
7. **Session expiry mid-use (any screen):** the next API call returns 401 → app shows a banner (not dismissible — the user must act) **"Your session has expired. Please log in again."**, clears client state, redirects to `/login`. If a form had unsaved input, the banner adds: **"Any unsaved changes were not saved."**
8. **Logout:** one click from the user menu on any screen, no confirmation needed (not destructive) → session revoked server-side → redirect to `/login` with **"You have been logged out."**

## Flow 2 — Log a new complaint (US-002, US-003)
**Trigger:** clerk clicks **"+ New complaint"** on `/complaints` (opens an inline panel, not a new route).

1. Fill citizen name (required, ≤100 chars, BR-014), phone (required, digits + optional leading `+`, 7–15 chars, BR-012), description (required, ≤2,000 chars, BR-006/BR-014).
2. Field-level validation on blur; a top-of-form error summary appears on submit if any field is invalid, each item linking to its field (accessibility requirement — see accessibility-strategy.md).
3. Submit → button disabled, spinner + **"Saving…"**.
4. **Success (201):** a dedicated confirmation state shows the new complaint number prominently (large monospace type) with a **Copy** button and the instruction **"Give this number to the citizen — they'll need it to check status later."** "Done" returns to the list, new complaint visible at the top (most-recent-first, FR-007).
5. **Failure — validation rejected server-side (422, defense in depth):** errors mapped back to the matching fields; anything unmappable shown as a general banner.
6. **Failure — network/timeout:** "The server is taking too long. Please try again."; all entered data is preserved, nothing is cleared.
7. **Failure — session expired mid-fill:** Flow 1 step 7 applies; the clerk is told the data was not saved and must re-enter it after logging in again.

## Flow 3 — Update complaint status and add a note (US-004, US-012)
**Trigger:** clerk expands a complaint's detail panel from `/complaints` and clicks **"Update status."**

1. The status control offers **only the statuses legally reachable from the current one** (BR-002: New→In Progress; In Progress→Resolved/Rejected; Resolved/Rejected→Closed, optional) — invalid transitions are not selectable, not merely rejected after the fact.
2. Optional free-text note field (FR-006).
3. Before submit, if the loaded detail is stale (a newer status-history entry exists server-side than what's on screen), a non-blocking banner appears: **"This complaint was updated by {clerk} a moment ago. Refresh to see the latest before making changes."** The clerk may still submit — BR-011 guarantees last-write-wins on current status while preserving **both** updates in history, so the UI warns rather than blocks (see ux-decisions.md decision 4).
4. Submit → **"Saving…"** → **Success:** status badge updates, a new entry appears at the top of the Activity/history list with the editing clerk's name and timestamp (FR-011).
5. **Failure — validation/network/timeout/session-expiry:** same patterns as Flow 2, steps 5–7.

## Flow 4 — Find, filter, and view a complaint; correct details; view audit history (US-005, US-007 n/a here — see Flow 5, US-008, US-009, US-013)
**Trigger:** clerk lands on `/complaints` after login (default route).

1. List loads, most-recent-first, filterable by status (segmented control, default "All"); a "Find by complaint number" quick box jumps straight to a match (this is what FR-005 requires: "find an existing complaint by number or from a list"), and a **"Search by name or phone"** box (UX-F1 — a UX addition with no backing FR, motivated by list growth/NFR-010 and a clerk fielding a call without the number, built on data clerks already see per FR-016; pending human confirmation, OQ-10) filters the list to partial matches, debounced ~300ms so it doesn't fire a request per keystroke; the settled result count or no-match message is announced via a `role="status"`/`aria-live="polite"` region (A11Y-13, see interaction-patterns.md). Search and status-filter combine (AND); clearing both returns to the full list.
1a. **Pagination (UX-F1, NFR-010):** the record set has no delete and no date filter in MVP, so it only grows. The list loads **25 rows at a time**, newest first, with a **"Load more"** button beneath the rendered rows — not numbered pages, since clerks scan top-to-bottom for recent activity rather than jumping to arbitrary pages. Clicking it appends the next 25 without disturbing scroll position or already-open rows. Changing the status filter or search term resets to the first page of the new result set. **States:** loading-more (button shows "Loading…", disabled, existing rows stay interactive), load-more error (button reverts, inline "Couldn't load more complaints. Retry." appears above it, existing rows unaffected), end-of-list (button replaced by static "All complaints shown" text).
2. Click a row → detail panel expands in place (see information-architecture.md — no dynamic route) showing full citizen name/phone (FR-016), description, current status, and a combined **Activity** timeline merging status history (FR-011) and edit history (FR-014), newest first, each entry showing what changed, previous → new value, editing clerk, and timestamp.
3. **Edit details** (name/phone/description) is available only within the edit window (default 7 days, A8); once passed, the action is visibly disabled with a tooltip/caption: **"Editing is only available within 7 days of logging a complaint."** Editing follows the same validation as Flow 2 and appends to the Activity timeline rather than overwriting silently (BR-008 symmetry).
4. **No delete control exists anywhere in this screen** — by design (BR-003, BR-008, US-013): there is nothing to confirm because there is nothing to remove.
5. **States:** loading skeleton; **empty, no complaints yet** — "No complaints logged yet. Create the first one."; **empty, filtered/searched** — "No complaints match this filter." (search adds the term: "No complaints match \"{term}\"."); **fetch error** — "Couldn't load complaints. Retry."; pagination states per step 1a above; session-expiry per Flow 1.

## Flow 5 — Citizen checks status (US-006, US-007, US-010, US-011)
**Trigger:** citizen opens the public URL (given verbally/on paper by a clerk) on any device.

1. Static HTML shell paints immediately from the CDN (no API call yet). In the background, the client fetches `GET /api/session` to seed the CSRF cookie/token, in parallel with hydration. **(A11Y-12)** The "Check status" button's label and its adjacent state-message text share one `role="status"`/`aria-live="polite"` container — the same convention as the Loading Indicator (component-spec.md #11) — so every transition across steps 1a–1d and 4 below is announced automatically to screen-reader users without a forced focus move.
   1a. **(UX-F3) While the seed request is in flight:** the complaint-number field is enterable immediately, but **"Check status" is `aria-disabled="true"` with its label showing "Preparing…"** rather than the normal "Check status" — so a citizen who types fast is never blocked from starting, only from submitting before the app can attach a valid CSRF token. There is no spinner-only state here; the label itself communicates progress. This typically resolves in well under a second and most citizens never perceive it.
   1b. **Seed succeeds:** the button becomes live, label reverts to "Check status," no visible transition beyond the label swap.
   1c. **Seed is slow (>4s):** the "Preparing…" label gains a small inline "Retry" text control that re-fires the seed request, so a citizen on a very slow connection isn't left staring at a button that never explains itself.
   1d. **Seed fails outright (network/5xx on the seed call):** the button stays disabled with the label "Unavailable — reload the page," and if the failure is specifically a cookie-blocked condition, the page shows the same "This page needs cookies enabled…" messaging as step 11 rather than a generic failure.
2. Citizen types a complaint number, taps **"Check status."** (only possible once the button is live per step 1a-b.)
3. **Blank/whitespace/malformed input:** the client performs the same cheap format check the API enforces and shows **"Enter a valid complaint number"** instantly, with *no network request* (FR-020/BR-015 mirrored client-side for speed; the API remains the binding contract — this is defence in depth, not a replacement).
4. Otherwise: `POST /api/lookup`; button disabled, **"Checking…"** shown.
5. **Success — found (200):** shows complaint number, status, date logged, and the fixed public status message for that status (see interaction-patterns.md for exact wording) — never the clerk's note, never name/phone (FR-009, BR-005, NFR-009).
6. **Not found:** clear message — **"We couldn't find a complaint with that number. Please check the number and try again, or contact the panchayat office."** (FR-010). No distinction is ever shown between "not found" and "invalid format" for malformed input (BR-015) — those are caught at step 3/the API boundary before any lookup.
7. **Server-side validation reject (400, defense in depth — e.g. a format edge case the client missed):** identical message to step 3: **"Enter a valid complaint number."**
8. **Rate-limited (429):** **"Too many attempts from this network. Please wait a minute and try again."** (UX-F4 — reworded from "this device": the limit is enforced per IP, and carrier-grade NAT commonly puts many citizens' phones behind one shared IP, so "device" was inaccurate) — soft wording, never a CAPTCHA or hard block (per the human's rate-limit decision).
9. **Service unavailable (503, e.g. DB failure — limiter fails closed):** **"The service is temporarily unavailable. Please try again in a few minutes."**
10. **Timeout (10 s abort or network error):** **"The server is taking too long. Please try again."**
11. **Cookies disabled** (the CSRF seed cookie can't be set, so the follow-up POST is rejected with a distinct CSRF error code): a specific, friendlier message replaces the generic error — **"This page needs cookies enabled to check your complaint status. Please enable cookies in your browser and reload the page."**
12. **JavaScript disabled:** a `<noscript>` block, visible without any script running, reads: **"This page requires JavaScript to check your complaint status. Please contact the panchayat office for help."**
13. **Success end state:** the citizen may clear the field and look up another number without reloading the page.

## Flow 6 — Admin account management (US-014, US-015, US-016)
**Trigger:** admin clerk opens `/accounts` (link visible only when `is_admin_clerk`).

1. List shows existing clerk accounts (username, role, created date) — **empty state** if only the admin's own account exists: "No other clerk accounts yet."
2. **If exactly one admin account exists**, a persistent advisory banner reads: **"Only one admin account exists. If it's locked out, nobody can create or reset accounts in-app. Consider creating a second admin account."** (addresses Q-015 with a UX default — see open-questions.md).
3. **Create account:** click **"+ New clerk account"** → enter username (3–30 chars, letters/digits/underscore, BR-016) and role (regular/admin) → submit. **Failure:** inline error for a taken/invalid username, nothing created. **Success:** a dedicated confirmation screen shows the system-generated one-time password once, in large monospace type, with a **Copy** button and the warning **"This password will not be shown again. Give it to {username} now."** The admin must check **"I have recorded this password"** before the **Done** button is enabled (see ux-decisions.md decision 3).
   3a. **(UX-F2) Guard against every exit path, not only Escape/Done, while the checkbox is unchecked:** (i) `Escape` is intercepted and does nothing (with a visible reason shown near the checkbox, as before); (ii) a `beforeunload` handler shows the browser's native "Leave site? Changes you made may not be saved" confirmation if the admin tries to close the tab or navigate to a typed URL/bookmark; (iii) a route-change guard intercepts in-app navigation (nav links, browser back/forward) and shows an in-app confirmation dialog — **"You haven't confirmed you've recorded this password. Leave anyway? You will not be able to see it again."** with "Stay" (default-focused) and "Leave without recording" actions. **(A11Y-15)** This confirmation dialog opens on top of the OTP dialog, but only one dialog is ever in the focus trap at a time — the OTP dialog's trap is suspended while the confirmation is open. `Escape` on this confirmation is equivalent to activating "Stay" (its default-focused action), since the confirmation itself is not exempt from normal Escape-to-cancel behaviour the way the OTP dialog is. On "Stay," the confirmation closes and focus returns to the "I have recorded this password" acknowledgment checkbox inside the OTP dialog, whose focus trap resumes. Checking the checkbox removes all three guards immediately. This closes the gap where tab-close, browser back, and typed-URL navigation previously bypassed the acknowledgment entirely.
4. **Reset password:** click **"Reset password"** next to an account → confirmation dialog — **"Reset the password for {username}? Their current session(s) will end and they'll need the new one-time password to log in."** → confirm → same one-time-password display pattern as step 3.
5. **Non-admin direct access (FR-019):** a regular clerk who reaches `/accounts` by URL sees a clear **"You don't have permission to view this page. Contact your admin clerk for account changes."** state with a link back to Complaints — never a silent redirect and never partial data.
