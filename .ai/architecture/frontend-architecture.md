# Frontend Architecture — Next.js 15 static export

rev 3 (2026-09-09). Binding: ADR-004 (static export, no SSR/ISR/route handlers/middleware, no Node
in production), ADR-010 (tooling, generated types, CSP hashing), ADR-013 (public page may require
JS), ADR-014 (UX baseline, one strings module). The API is the security boundary; **everything here
is UX, never enforcement**.

## 1. Project structure

```
web/
  next.config.mjs          # output: "export", trailingSlash: true, images.unoptimized
  .nvmrc                   # 22
  src/app/
    layout.tsx             # <html lang="en">, one stylesheet, skip link, no fonts, no analytics
    page.tsx               # "/" public lookup — prerendered shell + <LookupIsland/>
    login/page.tsx
    change-password/page.tsx
    complaints/page.tsx    # list + inline detail; NO dynamic segment (ADR-004)
    accounts/page.tsx
    not-found.tsx          # Screen 6
  src/islands/             # "use client" leaves: LookupIsland, LoginForm, ComplaintsApp, AccountsApp, ChangePasswordForm
  src/components/          # presentational only (component-spec.md #1–#12), no fetching
  src/lib/
    api.ts                 # the single fetch wrapper (§4)
    csrf.ts                # seed + token handling
    errors.ts              # API error code -> strings key
    auth.ts                # AuthProvider: session state, must_change_password, expiry handling
    format.ts              # complaint-number normalise/format + checksum mirror
  src/strings/en.ts        # EVERY user-visible string, typed keys (ADR-014 Q1)
  src/api-types.ts         # generated by openapi-typescript, COMMITTED, CI fails if stale
  src/styles/app.css       # one hand-written stylesheet, CSS custom properties (design-tokens.md)
  scripts/gen-csp.mjs      # post-build inline-script hashing (§8)
  headers.config.json      # single committed source for host headers + rewrites (§8)
```

No CSS framework, no component library, no icon pack, no `next/font`, no client-side analytics
(payload discipline, ADR-004 / AD-1).

## 2. Routing and rendering

| Route | Rendering | Island |
|-------|-----------|--------|
| `/` | prerendered static HTML; paints before any network call | one island: form, `fetch`, `AbortController`, result |
| `/login` | static shell | login form |
| `/change-password` | static shell | password form; nav suppressed while `must_change_password` |
| `/complaints` | static shell, all data client-fetched | list + inline detail panel; **selection is in-memory state, never a URL segment or query string** (AD-8: the complaint number must not enter URL, referrer or history) |
| `/accounts` | static shell | admin island; a `403` renders the explicit "no permission" state, never a silent redirect (FR-019) |
| anything else | `not-found.tsx` | — |

A committed host rewrite maps `/complaints/*` → the exported `/complaints` shell so a stray or
bookmarked deep link loads the app and lands on the list. The same rule is applied by the CI static
server so E2E tests exercise production behaviour.

**Client-side route guards are UX only.** `AuthProvider` redirects an unauthenticated user to
`/login` and a `must_change_password` user to `/change-password`; the API returns 401/403 regardless.

## 3. State handling

No state library. Three tiers, in order of preference:

1. **Local component state** for forms and dialogs — the default.
2. **`AuthProvider` context** for `{authenticated, username, is_admin_clerk, must_change_password, csrfToken}`, hydrated from `GET /api/session` on mount of any clerk route. The endpoint returns two variants (R2-3): with the session cookie present it returns the full authenticated object, which is what this provider consumes; with no cookie it returns `{authenticated:false, csrf_token}`, which is what the public page consumes. The generated types express this as a union discriminated on `authenticated`, so a component cannot read `username` without narrowing.
3. **Per-screen data hooks** (`useComplaints`, `useAccounts`) holding `{data, loading, error, hasMore, cursor}` — plain `useState` + `useEffect`, request-cancellation on unmount, and an explicit `refresh()`. `useComplaints` calls **`POST /api/complaints/search`** with **`{status?, complaint_number?, q?, cursor?}`** in the **body** — never a query string, because every one of those values is either PII or a lookup credential (R2-1). **The two search controls from the screen inventory stay two fields (rev 3, R3-1/ARCH-F1):**
   - `complaint_number` — the clerk's exact-match quick jump (FR-005/AC-005). The client sends what was typed; the server normalises it with `core.complaint_number.normalise()` (strip `-`/spaces, uppercase, `I/L→1`, `O→0`) and matches by **equality** on the canonical 9-symbol form. This is the field that makes the hyphenated `XXXX-XXXXX` a clerk reads off a receipt work at all — an `ILIKE` against `CHAR(9)` canonical storage can never match it.
   - `q` — free-text over **citizen name and phone only**, `ILIKE`, for "the lady who called about the drain".
   Sending both is allowed and ANDs. The client mirrors the format+checksum check on `complaint_number` for instant feedback (UX only; FR-020's authority is the API). Pagination appends (25 rows, "Load more") using the opaque cursor the server returned; the page size is fixed server-side and the client never sends a `limit`. Any filter or search change resets the cursor to null.

No global cache, no optimistic updates: at ≤6 clerks a refetch after a mutation is cheaper to reason
about than cache invalidation, and it is what makes the BR-011 staleness advisory honest.

## 4. API client

`src/lib/api.ts` is the **only** module that calls `fetch`. Every call:

- targets `${NEXT_PUBLIC_API_BASE_URL}` (build-time public value);
- sets `credentials: "include"` (cross-origin, same-site — the `__Host-` cookie rides along);
- sends `X-CSRF-Token` on every unsafe method, from `csrf.ts`;
- wraps an `AbortController` with a **10 s** timeout (NFR-011, uniform across all three core workflows);
- is typed against `src/api-types.ts` — a field the schema does not declare cannot be read;
- maps the error envelope's `code` to a strings key; an unknown code falls back to the generic message rather than rendering server text;
- **generates one `client_request_id` (`crypto.randomUUID()`) when the log-complaint form is first opened, keeps it in that form's state across every retry, and discards it only on a confirmed success or an explicit "start a new complaint"** (R2-6). Regenerating it on retry would defeat the whole mechanism, so this is the one piece of request identity the client owns and a Vitest case asserts the id is stable across a simulated timeout-then-retry. **Known bound, stated rather than assumed (rev 3, REL low):** the id lives in React state only, so it **does not survive a closed tab, a reload or a browser crash** — a clerk who closes the tab mid-timeout and re-enters the complaint gets a new id and therefore a genuine second record. Deliberate: persisting it would put a live request identity in `localStorage` for the same ~400 npm packages, for a case the "Check the list before entering it again" wording already covers. The de-duplication guarantee is scoped to *retries within one form session*.

Response handling rules:

| Condition | Behaviour |
|-----------|-----------|
| `401` on any authenticated call | clear client state, show the non-dismissible "Your session has expired" banner, focus it, redirect to `/login` (Flow 1 step 7). **This mapping is only safe because the API returns `401` for exactly one condition — "no valid session" (rev 3, ARCH-F3).** No field error, and specifically not a wrong current password, may arrive as a `401` |
| `422 invalid_current_password` on `POST /api/password/change` (rev 3, ARCH-F3) | render the error **against the `current_password` field** from `fields.current_password`, keep the session, keep the other field values, focus the field. Never a logout — rev 2 would have returned `401` here, so one typo logged the clerk out. **Rev 4 (R4-1): the forced-change screen has no current-password field at all** — a must-change session posts `new_password` only, because the OTP that opened it has already been destroyed — so this error can only arise on the voluntary change screen |
| `403` with `code: "must_change_password"` in the standard envelope (rev 3, ARCH-F7) | route to `/change-password`, suppress nav |
| `413 payload_too_large` | "That's too much text to send at once." — cannot occur from the UI's own fields (rev 3, SEC-S8) |
| `403` `forbidden` on `/accounts` | render the explicit permission state (FR-019) |
| `429` | render the countdown from `Retry-After`; disable submit |
| `503` | "The service is temporarily unavailable…" |
| abort / network error on a **GET or a search** | "The server is taking too long. Please try again." — form values preserved; Retry is safe because the call is idempotent |
| abort / network error on **`POST /api/complaints`** (rev 2, REL-F1) | **Never a bare "Retry".** The state reads: *"We didn't get a confirmation — your complaint may already have been saved. Check the complaints list before entering it again."* with two actions: **"Check the list"** (primary, refreshes and scrolls to the newest entries) and **"Try again"** (secondary, resends **the same `client_request_id`**, so the server returns the already-created complaint instead of a duplicate — R2-6/ADR-022). Form values are preserved either way |
| `200` with `duplicate: true` on `POST /api/complaints` | Treat as success, but show "This complaint was already saved — showing the existing record" and its complaint number, so the clerk does not read out a number for a record they think is new |
| CSRF-specific error on the public page | "This page needs cookies enabled…" (Flow 5 step 11) |

**CSRF seed lifecycle (public page).** On mount, `GET /api/session` runs *in parallel with hydration*;
the number field is enterable immediately while the button shows `aria-disabled` + "Preparing…";
>4 s adds a "Retry" affordance; outright failure sets "Unavailable — reload the page". After login and
password change the client replaces its token from the response body with the new **session-bound**
token; after **logout** the body carries a fresh **anonymous** token (ARCH-F4), which is what lets
the page immediately POST `/api/login` or `/api/lookup` without another round trip. The client stores
whatever the body returned and does not care which kind it is.

## 5. Strings module

`src/strings/en.ts` exports a flat, typed record (`export const S = {...} as const`). Rules enforced
by the CI grep (assertion 19 family): no user-visible literal in a component or island; every error
code has an entry; the `<noscript>` text lives in `layout.tsx` but is sourced from the same module at
build time. Adding Telugu later is a second file plus a resolver — no component changes (ADR-014 Q1).

## 6. Error and reload handling

- **Route-level error boundary** per screen renders "Couldn't load … Retry." with a retry action; it never renders raw error text. **Rev 2 (REL-F1): "Retry" is not universal.** A retry control may only be offered where the underlying call is idempotent — every `GET`, `POST /api/lookup`, `POST /api/complaints/search`. On `POST /api/complaints` the boundary and the form both use the "may already have been saved" state above. `POST /api/complaints/{id}/status` and `/details` keep a plain Retry: a duplicate there is one extra, visible, correctly-attributed history row, not a phantom complaint.
- **Chunk-load failure** (stale HTML shell requesting a chunk a promotion deleted — R14): the dynamic-import/asset helper catches `ChunkLoadError`/404-on-asset and shows "A new version is available — reload", not a blank screen. One Playwright spec serves an exported shell with a removed chunk and asserts the prompt.
- **Global window error / unhandledrejection** handler logs to the console only — there is no error-tracking SaaS (ADR-011) and nothing is sent anywhere.
- HTML entry points are served `no-cache`, hashed assets `immutable`, so the skew window is a single navigation.

## 7. Accessibility hooks (from ADR-014 / accessibility-strategy.md)

Shared `role="status"`/`aria-live="polite"` regions: one on the public page carrying the button
label + state message (A11Y-12), one beside the clerk search box reused for result counts and
pagination (A11Y-13). Focus management: error summaries and the session-expiry banner receive focus;
the OTP dialog traps focus and suspends its trap while the leave-confirmation dialog is open
(A11Y-15). `<html lang="en">`. All of this is component behaviour, asserted by Vitest and Playwright.

## 8. CSP hashing and host configuration

`npm run gen:csp` (post-`build`, ~40 lines, no dependency) parses every file in `out/**/*.html`,
computes the SHA-256 of each inline `<script>`, and writes `headers.config.json` with a **per-path**
`script-src 'self' 'sha256-…'`. That one file is consumed by the Render static site *and* by the CI
static server, so tests see production headers.

Header set: `Content-Security-Policy: default-src 'self'; connect-src 'self' https://api.<domain>.in;
img-src 'self' data:; style-src 'self'; script-src 'self' 'sha256-…'; frame-ancestors 'none';
base-uri 'none'; form-action 'none'` plus `Referrer-Policy: no-referrer`, `Permissions-Policy`,
`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`.

`style-src 'self'` blocks React inline `style` props — **inline styles are forbidden in the
codebase** and grepped in CI. The recorded fallback if the spike fails (ADR-010 option c) is
`script-src 'self' 'unsafe-inline'` as a *stated weakening* with the ADR amended; it is not taken
silently. **Spike task for /plan:** run one real `next build`, count inline scripts per page, confirm
the hash set is deterministic for a fixed input and that Render accepts per-path headers of that size.

## 9. Build gates

| Gate | Command | Failure |
|------|---------|---------|
| Types | `tsc --noEmit` | any error |
| Lint | `biome ci .` with `security` + `correctness` groups explicit | any error |
| Generated client types current | regenerate `openapi-typescript` from the CI-dumped schema and diff against the committed `api-types.ts` | stale ⇒ fail |
| **Byte budget (AD-1/C8)** | parse `next build`'s route table: **first-load JS on `/` ≤ 120 KB gzipped**, CSS ≤ 8 KB | over ⇒ fail the build |
| Source hygiene grep | no `dangerouslySetInnerHTML`, `innerHTML`, `eval(`, `new Function(`, inline `style=`/`style={`, or an `href` built from user input without the scheme allow-list | any hit ⇒ fail |
| Unit | `vitest run` — lookup island format check + error/timeout rendering, login form, list rendering | any failure |
| CSP | E2E assertion against the deployed preview: no `unsafe-inline`/`unsafe-eval`, every inline script hashed, `connect-src` names exactly the API origin | any failure |

If the 120 KB gate cannot be met, the named fallbacks (ADR-004) are: (i) hand-written ~2 KB static
public page with vanilla JS while the clerk app stays Next.js, or (ii) accept >3 s and record it as
a requirement change. Both are GATE-visible, not build-time improvisation.

## 10. What the frontend must never do

Hold or persist an OTP (no `localStorage`, no URL, no query string) · put a complaint number, a
citizen name or a phone number in a URL, query string or `history` entry — **search criteria go in a
`POST` body** (R2-1) · issue a request with any method other than `GET` or `POST` (R2-2) · offer a
bare "Retry" on complaint creation (R2-6) · decide authorization · trust a client-side validation result
as the contract (FR-020's authority is the API) · call any origin other than the API · load a
third-party script, font or tag manager · render server-provided HTML.
