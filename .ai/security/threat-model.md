# Threat Model — panchayat-complaint-tracker

rev 3 (2026-09-09) · Owner: solution-architect · Method: STRIDE over the assets and components
defined in `.ai/architecture/solution-architecture.md`. Controls are specified in
`.ai/architecture/security-architecture.md`; this document is the coverage record.

**Status vocabulary (exact):** `mitigated` — a named control in a named component reduces the threat
to an acceptable level and is testable. `accepted` — understood, not controlled (or only partly),
with the reason recorded. `n-a` — the threat has no attack surface in this system.

## Assets, ranked

| # | Asset | Why it matters | Worst outcome |
|---|-------|----------------|---------------|
| A1 | Citizen PII (name, phone, complaint text) | NFR-008/009, BR-005, BR-009 | public exposure of a villager's contact details and complaint |
| A2 | The audit trail (status + edit history) | FR-011/FR-014, BR-008 — the core deliverable | a dispute becomes unresolvable |
| A3 | Clerk credentials and sessions | gateway to A1 and A2 | full impersonation of the office |
| A4 | Complaint numbers | the citizen's only lookup credential | mass status disclosure by enumeration |
| A5 | Availability of the public lookup | NFR-001/007 | citizens return to phoning/visiting the office |
| A6 | Backups | the only recovery path | full PII export in the wrong hands |
| A7 | Build and deploy pipeline | reaches all of the above | arbitrary code in production |

**Trust boundaries.** B1 browser ↔ API (the security boundary — the frontend enforces nothing);
B2 API ↔ Postgres (Fly private network, `sslmode=require`); B3 developer/CI ↔ production (human
promotion only, no deploy credential in CI); B4 npm/PyPI ↔ build (the weakest boundary — see #15).

## Threats

| # | Threat | STRIDE | Asset | Mitigation / reason | Status |
|---|--------|--------|-------|---------------------|--------|
| 1 | Password brute force against a clerk account | S | A3 | Three-tier login limiter (per-IP ceiling short-circuits first, username+IP blocks, per-account `429 + Retry-After`), Argon2id cost, `security_event` records every failure. The per-IP tiers rest on the **peer-gated** client-IP derivation (#60), not on a believed header | mitigated |
| 2 | Credential stuffing / weak or reused password | S | A3 | ≥12 chars, not username-similar, not numeric, not in the vendored ~10k common-password list; per-IP ceiling is not cleared by a success | mitigated |
| 3 | Session token stolen by page script (XSS or dependency) | S | A3 | Token is in an `httpOnly` `__Host-` cookie, never in `localStorage` or a response body; no JWT | mitigated |
| 4 | Session token stolen on the network | S | A3 | TLS everywhere, `Secure` cookie, HSTS `max-age=31536000; includeSubDomains`, edge HTTP→HTTPS redirect verified at /release | mitigated |
| 5 | Session fixation | S | A3 | **Login always mints a new token and a new row, and revokes the session presented in that request's own cookie** (ADR-021/R2-4) — so a token an attacker planted in the victim's browser is exactly the one destroyed, and the victim leaves with a token the attacker has never seen. Sessions on the clerk's *other* devices are deliberately untouched (office desktop + phone), and a password change revokes all of them. DB stores only the token hash. Rev 1 said "revoke old on login" ambiguously and the API contract read it as "no rotation"; test SEC-T23 now pins the behaviour | mitigated |
| 6 | Phishing a clerk's credentials | S | A3 | No MFA at launch (offered, no requirement); ≤6 accounts on one office network; detection via `security_event` and the 45-min idle window. TOTP for the admin clerk remains a costed option | accepted |
| 7 | One-time password captured by a malicious npm package inside the clerk page | S/I | A3 | ADR-007 H-B decision: the OTP transits the client so FR-017/FR-018 remain usable in-app. Bounded by 72 h expiry, forced change, session revocation, `connect-src`, `no-store`, no client persistence — and, **from rev 4 (R4-1), by real consumption at login**: the login that uses the OTP overwrites `password_hash` with the Argon2 hash of a discarded 256-bit random value, so the captured OTP stops authenticating the moment anyone uses it. Rev 2 called the OTP "single-use" while a password change was the only thing that retired it; rev 3 cleared `password_is_otp` at login and called that consumption, but the OTP's own hash was still the account password — the "spent" OTP kept working *and* clearing the flag switched off the 72 h expiry check that is guarded by it, turning a three-day credential into a permanent one. That is why the hash, not a flag, is destroyed. **Still not eliminated**: an attacker who captures and uses the OTP before the clerk does gets one must-change-confined session, and the clerk's failed login is the alarm | accepted |
| 8 | CSRF on an authenticated write | T | A2 | `SameSite=Lax` + `Origin` allow-list + session-bound `X-CSRF-Token` (`compare_digest`), rotated with the session; no exemption list exists in the codebase | mitigated |
| 9 | CSRF-driven enumeration through visitors' browsers on the public lookup | T/I | A4 | The public POST is deliberately **not** exempt: stateless HMAC token over the `__Host-csrfseed` cookie, plus `Origin` check — spreading guesses across victim IPs fails | mitigated |
| 10 | SQL injection | T | A1,A2 | SQLAlchemy bound parameters everywhere; the single hand-written statement (limiter upsert) is a bound `pg_insert` construct; Ruff `S` rules; no string-built SQL | mitigated |
| 11 | Field injection / mass assignment (e.g. setting `is_admin_clerk` or a status directly) | T/E | A2,A3 | Every request model is Pydantic with `extra="forbid"`; services accept explicit fields only; role and status are never bound from input | mitigated |
| 12 | Illegal status transition via a direct API call | T | A2 | Frozen transition map checked inside the row-locked transaction (BR-002); the UI offering only legal options is cosmetic | mitigated |
| 13 | Editing citizen details after the 7-day window via a direct API call | T | A2 | `now() < created_at + EDIT_WINDOW_DAYS` enforced in `services.complaints`; the disabled control is cosmetic | mitigated |
| 14 | Tampering with or deleting audit history | T/R | A2 | No delete endpoint anywhere; `before_execute` hook raises on `UPDATE`/`DELETE` against the three append-only tables; grep assertion; optional `REVOKE UPDATE, DELETE` for the app role | mitigated |
| 15 | Malicious npm or PyPI release enters the build | T | A7,A1 | Committed lockfiles, exact versions, `npm ci --ignore-scripts`, `npm audit signatures`, 7-day minimum release age, auto-merge only for patch/minor of already-present packages, two eyes for any new dependency — **no control detects a zero-day malicious release**; ~350–450 npm packages run with clerk-session capability (R16) | accepted |
| 16 | Compromised CI produces or deploys a malicious artefact | T | A7 | No deploy job and no deploy credential in CI; all third-party actions SHA-pinned; `permissions: contents: read`; no `pull_request_target`; no secrets to fork PRs; `main` protected (PR required, green checks, linear history, no force-push); production reached only by a human `fly deploy` | mitigated |
| 17 | DNS hijack, domain expiry or a lapsed payment card | T/D | A5 | Registrar and billing owned by the human (ADR-002 Q3); renewal is a /release handover item; no technical control exists in the application | accepted |
| 18 | A clerk denies making a status change | R | A2 | Every change writes an append-only history row with actor `user_id` and timestamp, in the same transaction; both writers survive a concurrent update (BR-011) | mitigated |
| 19 | Denial of an account creation or password reset | R | A3 | `security_event` rows for `account_created` and `password_reset_issued` with actor, derived IP and timestamp, inside daily backups | mitigated |
| 20 | An operator with `psql` alters or deletes history rows | R | A2 | Append-only is enforced at the application layer, not the database role (the platform may not permit a second role). Support access is human-owned and rare; recorded rather than claimed as controlled | accepted |
| 21 | Citizen name or phone rendered on the public page | I | A1 | Public DTO is exactly `{complaint_number, status, date_logged, public_update}` with `extra="forbid"`; a test asserts neither string appears in the serialised response | mitigated |
| 22 | Clerk free-text note leaking PII on the public page | I | A1 | ADR-013: `public_update` is an enumerated message derived from status; the clerk note is clerk-only and never in the public DTO | mitigated |
| 23 | Complaint-number enumeration / bulk guessing | I | A4 | ≥40 random bits (8 Crockford base32 symbols) + checksum rejected before any DB access, non-sequential, POST-only lookup, 20/IP/min limiter, no listing endpoint on the public allow-list (BR-010) | mitigated |
| 24 | Bulk PII exfiltration through the authenticated clerk detail endpoint | I | A1 | **Downgraded from `mitigated` in rev 2 (SEC-F4) — the honest status.** The attack path, named: any clerk session can call `POST /api/complaints/search`, collect every complaint id, and then walk `GET /api/complaints/{id}`, each of which returns full name and phone by requirement (FR-016). Response minimisation only forces one request per record; it does not stop the walk, and no clerk lacks list access. Controls that **bound** it (re-keyed in rev 3, **completed in rev 4, R4-2**): the ceiling `RATE_LIMIT_DETAIL_PER_HOUR = 120`, scope `detail`, keyed on **`user_id`**, applied to every response carrying name or phone **in any form** — `GET /api/complaints/{id}`, **`GET /api/complaints/{id}/activity`** (edit-history `previous_value`/`new_value` for a `citizen_name`/`citizen_phone` edit **are** the name and the phone), `POST /api/complaints/{id}/status`, `POST /api/complaints/{id}/details` and `POST /api/complaints`; plus a new scope **`search` at 120/user/hour** on `POST /api/complaints/search`, which returns 25 records per call and was previously **unbounded**. Rev 2 keyed the ceiling on the session hash and put it on one route; rev 3 fixed the key but defined coverage as "routes whose `response_model` declares `citizen_name`", which is precisely why `/activity` and `/search` escaped — neither declares that field. Coverage is now an explicit per-route PII classification table (backend §5, repeated in the contract, read by SEC-T29). **What this actually buys, stated honestly:** 120 detail reads/hour, and 120 × 25 = **3 000 search rows/hour**. At pilot scale 3 000 rows is the whole complaint table — so the ceiling bounds the **rate** of a bulk walk (a sustained hour that leaves `throttle_detail`/`throttle_search` rows, instead of the table in one minute), **not the total an attacker can eventually obtain**. Plus the 45-min idle window, 9 h absolute, and `connect-src`. Read auditing (`complaint_viewed`) was reconsidered and still rejected (OQ-9): 1–5 known clerks all legitimately read everything, so the events would be noise nobody reads. **Residual accepted: a patient hijacked session, or a malicious npm package in the clerk page (#15), can still exfiltrate the contact list over hours** | accepted |
| 25 | Complaint number, citizen name or phone leaking via URL, referrer, browser history or the gunicorn access log | I | A1,A4 | **Strengthened in rev 2 (SEC-F3/ARCH-F1):** rev 1 kept the number out of URLs but left clerk search as a `GET` with `?q=`, which would have put names and phone numbers straight into the access log the redaction filter does not cover. Now binding: **no sensitive value in any path segment or query string**, so lookup is `POST /api/lookup`, clerk list/search is `POST /api/complaints/search` with a JSON body and an opaque cursor, clerk detail selection is client state, and path parameters carry only an opaque internal id. `Referrer-Policy: no-referrer`; the values are on the never-log list; a CI grep asserts no path parameter is named `number`/`phone`/`name`/`q` (observability §1) | mitigated |
| 26 | PII or credentials written to logs or `security_event` | I | A1,A3 | Explicit never-log list, a redaction filter, and tests asserting the submitted password and issued OTP appear in no captured record or event row | mitigated |
| 27 | Citizen data reaching a third-party processor | I | A1 | **Re-classified `n-a` → `accepted` in rev 3 (SEC-S11): "no third party" was never true.** No *discretionary* processor exists — no error tracker, no analytics, no tag manager, no CDN-hosted script or font, no AI/LLM (ADR-011, ADR-012), and every package is bundled at build time and served from our own origin. But the citizen database is stored and processed by **Fly.io** (machine + Managed Postgres + platform backups, all in `bom`) and the clerk/citizen browser sessions transit **Render**'s CDN for the static shell (no citizen data in the bundle — A-T1a). Those are two data processors under any reading of DPDP, they hold or route the data by design, and the mitigations are contractual and residency-based (region `bom`, encryption at rest, TLS, ADR-009), not technical controls we own. Recorded as accepted so the processor list at /release names Fly and Render rather than claiming there is none | accepted |
| 28 | Backup copy exfiltrated, **and** the single-vendor backup gap | I/D | A6 | **Downgraded in rev 2 (REL-F4/SEC-F15): rev 1 claimed a control that is switched off.** For the copies that exist — Fly's platform backups — encryption at rest is verified at signup and access is the Fly account, which is the human's. The off-platform monthly dump *would* be `age`-encrypted before leaving the machine, to a scoped-credential destination with a ~90-day lifecycle, but **it does not run: OQ-2 has no destination**. So the accepted residual is stated plainly: *every copy of the citizen database lives with one vendor; a vendor account loss, billing termination or region-wide data event has no independent recovery path, and nothing older than the platform's retention (~7 days, to confirm) exists anywhere.* Go-live is **not** gated on closing this; /release asks once more. Naming a destination retires it for ~$0–1/mo and moves this row back to `mitigated` | accepted |
| 29 | Loss or compromise of the backup encryption key | I/D | A6 | Single named key holder (the human, ADR-002 Q6); no escrow exists, so key loss means the off-platform copies are unrecoverable and platform backups remain the only path. A fallback person is a /release recommendation, not a control | accepted |
| 30 | Username enumeration from response differences | I | A3 | One generic message for unknown user and wrong password, identical status code and body shape; login failures never distinguish the cases | mitigated |
| 31 | Username enumeration via login response timing (Argon2 runs only for existing users) | I | A3 | Not equalised: a dummy-hash path was considered and judged not worth the code at ≤6 accounts on a per-IP-limited endpoint. The account set is also known to everyone in the office | accepted |
| 32 | Route, schema and clerk-UI enumeration from the shipped bundle | I | A7 | Accepted by construction under ADR-004: the static bundle is public, so paths and field names are readable. `/docs`, `/redoc`, `/openapi.json` → 404 is hygiene, not a control. **Authorization is the control** (deny-by-default over the whole route table) | accepted |
| 33 | Flood of public lookups (availability + guessing) | D | A5,A4 | Atomic Postgres fixed-window limiter, 20/IP/min, config-driven; the key comes from the **peer-gated** derivation (#60), not a believed header; IPv6 keyed by /64; unparseable ⇒ one shared bucket (fail closed); soft 429 wording, never a CAPTCHA or hard block | mitigated |
| 34 | Unauthenticated flood grows an append-only or unswept table until the DB degrades | D | A5 | **Scope corrected in rev 3 (SEC-S2): this row covers three tables, not one.** (a) **`session`** — ADR-007 H-A: no anonymous session rows exist at all, so a flood writes none; that control holds unconditionally. (b) **`rate_limit_counter`** — swept, see #35. (c) **`security_event`** — append-only and *undeletable by the application*, which is why the rev-2 wording "an anonymous flood cannot grow a table" was too broad: a `throttle_*` row per refused request would have been exactly such growth (now #64), and so was a `login_failure` row per wrong password, which rev 3 left unbounded and **rev 4 bounds to one row per `(actor_username_hash, derived_ip, 15-min window)` with none at all once the tier-1 throttle is active** (R4-5, observability §2). ADR-007 H-A: **no anonymous session rows exist at all** — that is the actual control for (a), and it holds unconditionally. The zero-SQL property is narrower than rev 1 implied and is restated precisely (R2-3/SEC-F9): `GET /api/session` executes **zero SQL only on the anonymous variant, i.e. when no session cookie is presented** — which is exactly the path a flood takes. When a cookie *is* presented the endpoint reads one indexed session row like any authenticated request, and is covered by session expiry and the authenticated posture instead. The burst test therefore sends no cookie and asserts an unchanged row count with lookups still serving 200s | mitigated |
| 35 | Limiter-table growth by rotating keys (e.g. one row per invented username, or a rotating source IP) | D | A5 | Per-IP ceiling short-circuits before any username-keyed row is written; key component is a fixed-width `h(username)`; **rev 2 (PERF-F2) adds a scope-agnostic bounded sweep** on every window rollover, because rev 1's per-key cleanup never touched rows whose key never recurs — the exact shape of this threat. **Rev 3 (ARCH-F2/R3-9) corrects the statement itself: PostgreSQL has no `DELETE … LIMIT`**, so the sweep is `DELETE FROM rate_limit_counter WHERE ctid IN (SELECT ctid FROM rate_limit_counter WHERE window_start < now() - make_interval(hours => 2) LIMIT 500)`, and the `window_start` index ships in the initial migration (R3-10) so it is an index range scan from the first request. A burst test (PERF-T26) asserts the row-count ceiling. Same peer-gating as #60 limits how cheaply keys can be rotated | mitigated |
| 36 | Attacker locks the office out by failing logins against a known username | D | A3,A5 | **Re-argued in rev 2 (SEC-F6) after removing the "recent-success IP is exempt" carve-out, which had no store behind it and therefore was not a control.** The argument now rests on one property only: **there is never a hard lock.** Tier 3 is an immediate `429 + Retry-After ≤5 s` with no thread sleep and no lockout flag, so the worst a remote attacker can inflict on a clerk typing the correct password is a ≤5 s pause. Tiers 1 and 2 are keyed by IP and username+IP, so the attacker's own address absorbs the blocking. `unlock-account` remains the break-glass. What is *not* claimed: a distributed attacker can keep tier 3 permanently warm, which means a permanent ≤5 s login delay for the office — annoying, not a lockout | mitigated |
| 37 | Oversized request bodies exhaust memory or storage | D | A5 | **Rev 3 (SEC-S8) adds the control that actually runs first:** middleware rejects any request whose `Content-Length` exceeds `MAX_REQUEST_BODY_BYTES = 65536` with `413 payload_too_large` **before the body is buffered or JSON-parsed**, and caps the read for length-less streams at the same figure (backend §2, security §6, test SEC-T31). 64 KB is ~30× the largest legitimate body. Rev 2 relied on Pydantic `max_length`, which only applies *after* the whole body is in memory and parsed, plus "platform edge body limits" — a limit nobody had read on a layer we do not configure. Field maxima (name 100, description 2000, phone 15, username 30) and `extra="forbid"` remain the second layer | mitigated |
| 38 | Concurrent logins exhaust the 512 MB instance through Argon2 memory | D | A5 | `m=9216 KiB` chosen for this instance (OWASP's 19 MiB rejected with the arithmetic recorded); threadpool capped at 4 tokens/worker ⇒ ≤8 concurrent hashes ≈72 MB transient; login limiter bounds the burst; memory alert at ~420 MB | mitigated |
| 39 | Connection exhaustion / slowloris against the single machine | D | A5 | Platform edge fronts the machine; gunicorn `--timeout 30`, `--keep-alive 5`, worker recycling. No application-level connection control and no HA — a determined layer-7 flood takes the API down | accepted |

| 43 | Bypassing `must_change_password` with a bookmarked deep link or direct API call | E | A3 | Enforced in middleware on every authenticated request except change-password, logout and `GET /api/session`; tested with a direct API call while the flag is set | mitigated |

| 60 | **Attacker chooses their own rate-limit bucket by forging `Fly-Client-IP` or `X-Forwarded-For`** (new in rev 2, SEC-F1) | S/D | A3,A4,A5 | Rev 1 said "prefer `Fly-Client-IP`, otherwise the XFF rule", which trusts a header on the strength of a platform habit — and a wrong hop count or an unfiltered header makes the limiter key attacker-chosen, silently voiding #1, #23, #33 and #35. Rev 2 (ADR-020 rewritten): the immediate **peer address** is taken from the ASGI scope first; both headers are read **only** when that peer is inside the explicitly configured `TRUSTED_PEER_CIDRS`, and are otherwise discarded entirely in favour of the peer address. Rev 3 saw the danger — uvicorn rewrites `scope["client"]` from `X-Forwarded-For` **before application code runs** — but mislocated the mechanism, prescribing "start the server without `--proxy-headers` / `--forwarded-allow-ips`". **Rev 4 (SEC-F1) fixes the diagnosis and the control:** gunicorn has **no `--proxy-headers` option**, and under `uvicorn_worker.UvicornWorker` uvicorn's `Config.proxy_headers` defaults to **True** with gunicorn's `forwarded_allow_ips` (default `127.0.0.1`, env `FORWARDED_ALLOW_IPS`) passed into it — so `ProxyHeadersMiddleware` is in the stack and rewriting the peer *with no flag present anywhere*. Rev 3 would have shipped the vulnerability with a green test. The control is now an in-repo worker subclass, `app/worker.py::RawPeerWorker`, with `CONFIG_KWARGS = {"proxy_headers": False, "forwarded_allow_ips": []}`, run as `--worker-class app.worker.RawPeerWorker` (infrastructure §3); `core/client_ip.py` is the only interpreter of `Fly-Client-IP` and `X-Forwarded-For` (grep-enforced; `X-Forwarded-Proto` has no consumer at all). `selfcheck` fails startup if `TRUSTED_PEER_CIDRS`/`TRUSTED_PROXY_HOPS` is unset **or if the effective uvicorn config has `proxy_headers` true, a `ProxyHeadersMiddleware` is in the built stack, or `FORWARDED_ALLOW_IPS` is set** — behavioural assertions, not an argv grep. **SEC-T21** runs a real process started with the container CMD and asserts the limiter key's **value** is the loopback peer (case 1), that the gate is not inverted (case 2), and — new in rev 4, SEC-F5 — that **two real client addresses yield two distinct keys** (case 3), which is the silent failure mode of a `TRUSTED_PEER_CIDRS` that does not match Fly's proxy: everything collapses into one bucket and looks like a flood (runbook §12.3). /release repeats cases 1 and 3 against production. `.claude/project-config.md`'s `start:` line must adopt the worker class and drop both flags at /plan | mitigated |

| 63 | **A departed or dismissed clerk retains access** (new in rev 2, SEC-F13/ARCH-F10) | S/E | A1,A2 | There is **no** `disabled_at` column and no disable endpoint (decision R2-10). The documented procedure is: the admin issues a password reset for that account and **discards** the OTP — which revokes every live session immediately, replaces the credential with one nobody has seen, and lets it expire in 72 h (R2-5), after which the account cannot be logged into at all. History rows keep the person's name, as BR-008 requires. **Accepted, not mitigated, because the control is a runbook step with no system affordance**: nothing marks the account as offboarded, it still appears in the accounts list, and nothing reminds a future admin why. Written up in security-architecture §3 and infrastructure §11. A `disabled_at` column is a small additive migration if turnover ever justifies it | accepted |
| 64 | **Unauthenticated flood grows `security_event` through throttle rows** (new in rev 3, SEC-S2) | D | A5 | `security_event` is append-only *and the application cannot delete from it* — the `before_execute` guard raises on any `DELETE` against it, deliberately (#14). Rev 2 wrote a `throttle_*` row on **every** `429`, including on the unauthenticated `lookup` and `login_ip` scopes, so an attacker at 20 rps added ~72 000 undeletable rows an hour: the one table in the system that a flood could grow without bound and that no sweep is allowed to shrink, inside the daily backups. Control: the limiter's `RETURNING count` already knows the crossing point, so a `throttle_*` event is written **only when `count == limit + 1`** — once per `(scope, key, window_start)`. The same flood now produces one row per window per key (≤60/hour per scope even with per-second key rotation, and key rotation is itself bounded by the peer-gated IP derivation, #60). **Rev 4 (R4-5/SEC-F4) closes the other half of the same hole**: `login_failure` was still written once per wrong password, i.e. up to the tier-1 ceiling (100/15 min/IP) of permanent rows before any throttle fired. It is now at most **one row per `(actor_username_hash, derived_ip, 15-minute window)`**, and **zero** once the `login_ip` counter is past its limit, because the short-circuit runs before the event service. Arithmetic in observability §2; test **SEC-T33**. The operator signal is unchanged: "this key was throttled / was failing, in this window". Backend §5, observability §2, test **SEC-T28**. Recovery if it ever does grow: a bounded manual `DELETE` run by the human as the **database owner role** — not the application role in `DATABASE_URL`, which has `UPDATE`/`DELETE` revoked on this table (#14) — via `fly postgres connect`, logged in the office log (runbook §12.4, #20) | mitigated |
| 65 | **A hijacked or scripted clerk session floods the complaint and account tables with records that can never be deleted** (new in rev 3, SEC-S4) | D/T | A2,A5 | BR-008 forbids hard deletes anywhere, so every inserted complaint and every created account is permanent; the only "clean-up" is Rejecting complaints one at a time, which itself writes history rows, and there is no account-delete capability at all (R2-10). Rev 2 had **no ceiling on authenticated writes** — a stolen session or a malicious dependency in the clerk page could insert thousands of permanent rows in minutes and there was no recovery short of a backup restore. Control: limiter scope `write`, key `user_id`, `RATE_LIMIT_WRITE_PER_HOUR = 60`, on `POST /api/complaints`, `POST /api/accounts` and — **added in rev 4 (R4-5)** — `POST /api/accounts/{id}/reset-password`, which was the one remaining uncapped permanent-state-change route (a scripted reset loop revokes a victim's sessions repeatedly and burns credentials); `429` over it and a `throttle_write` event on the crossing request. **Corrected arithmetic (rev 4, SEC-F6): 60/hour is 2–3× a busy clerk's real peak of 20–30 complaints/hour**, not the 20× rev 3 claimed — still above any real day, but close enough that the runbook says investigate and confirm with the office rather than assume compromise. Status updates and detail edits are excluded on purpose, and the exclusion is bounded rather than open: they create no new record, they are **counted by the `detail` scope (120/user/hour)**, and each one appends **at most ~3 history rows** (status, note, and the changed field) — so the worst case through those routes is a few hundred history rows an hour, all of them attached to existing complaints and all visible in the activity trail. Backend §5, security §7, test **SEC-T30**. Residual: 60 junk complaints/hour is still permanent pollution — bounded and detectable, not prevented | mitigated |
