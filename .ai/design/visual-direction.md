# Visual Direction

**Type:** system font stack only (no web-font download) — 16px/1rem body, 1.5 line-height, one modest scale up to 28px for page headings, plus a distinct large monospaced treatment for complaint numbers and one-time passwords.
**Color:** a single deep-green primary (`#146C43`, 6.46:1 on white) for actions and links, near-black text (`#1A1A1A`, ~19.5:1), light neutral backgrounds/borders, and five status colours chosen individually for ≥4.5:1 text contrast — never colour-only, every status also carries a text label.
**Density:** low-to-medium — generous spacing and large touch targets over compact data-grid density, because the office handles a handful of complaints a day, not hundreds on screen at once.
**Deliberately excluded:** gradients, glassmorphism, drop-shadow "elevation," decorative illustration or stock photography, animation/motion beyond an optional 150 ms fade, icon fonts/icon packages, dark mode, and the card-with-shadow pattern for simple rows (borders/dividers instead).

**UX-F6 (rev 2) — status icons considered and rejected, not merely omitted by default.** A zero-byte per-status Unicode glyph (e.g. a filled/outlined circle or check-mark character) alongside each status badge's text label was explicitly considered, given driver U1's literacy/language concerns. It was rejected for MVP because: (1) the status badge's text label is already the primary signal and is never colour-only (accessibility-strategy.md), so a glyph would be redundant rather than additive for a screen-reader user; (2) common Unicode glyphs that read unambiguously as "in progress" vs. "resolved" vs. "rejected" across fonts/platforms without a supplied icon set are surprisingly hard to pick well (e.g. an hourglass glyph renders as full colour emoji on some platforms and a thin monochrome glyph on others, which is inconsistent, not calming); (3) a badly-chosen glyph risks being read aloud by some screen readers as its Unicode name (distracting) while others skip it — an inconsistent experience is worse than no glyph. This is revisited if a future brand pass (OQ-2) supplies a proper icon set with tested screen-reader behaviour.
**Rationale:** every exclusion and every choice above traces to the drivers in ux-strategy.md — not a generic admin-dashboard look, and not decoration for its own sake.

## Why this direction, not a "SaaS admin dashboard"
The default temptation for a two-role, list-and-detail tool is a dashboard template: sidebar, cards with shadows, a chart or two, an icon library, a dark-mode toggle. None of that fits this product:
- **There is no dashboard content.** No analytics, no cross-clerk reporting, no KPI cards are in scope (Future scope only) — a dashboard shell with nothing to show is worse than no shell.
- **The performance budget forbids the tooling a dashboard template assumes.** tech-stack.md caps the public route at ≤120 KB gzipped first-load JS, explicitly rules out a CSS framework, component library, icon package, and `next/font` — the entire clerk app must also stay light because it ships in the same build. A visual language built from hand-written CSS and system fonts is not a compromise here; it is the only option inside the budget.
- **The users are not dashboard users.** 1–5 clerks doing a few minutes of data entry per complaint, and citizens on cheap Android phones with variable literacy and possibly a non-native language (drivers U1, U2, U7, U9) need plain, high-legibility, low-cognitive-load screens — closer to a well-designed paper form than a control panel.
- **Card-with-shadow and gradient/glassmorphism decoration communicate "modern SaaS product," not "trustworthy village-office record."** The correct feeling is calm and official, not flashy — plain borders, generous whitespace, and one confident accent colour do that; drop shadows and gradients would work against it and cost bytes for no functional gain.

## Color direction in more depth
- **Primary — deep green `#146C43`.** Chosen over a generic corporate blue for two concrete reasons: (1) it reads as "civic/agrarian" rather than "fintech dashboard," fitting a panchayat (village government) context without resorting to a literal illustration or flag colour that hasn't been supplied (see open-questions.md OQ-2 — no brand assets exist yet); (2) it doubles cleanly as the "positive/resolved" status colour, so the same hue that invites action also signals a good outcome, which is a small but real coherence win with zero extra cost.
- **Neutrals** are warm-leaning greys, not pure blue-greys, to avoid the "cold enterprise tool" read while staying unmistakably plain and legible.
- **Status colours** (blue for New, amber for In Progress, green for Resolved, red for Rejected, grey for Closed) follow the most widely understood convention for progress states, each individually contrast-checked (see design-tokens.md) rather than picked from a generic UI-kit swatch.

## Density and layout direction
Plain stacked forms, borders/dividers instead of cards, no more than two columns anywhere (list beside detail on wide clerk screens only), and a single consistent spacing rhythm (4px base unit). The public page is deliberately the simplest screen in the product — one field, one button, one result block — because it is the highest-stakes screen for a first-time, possibly low-literacy user on a slow connection (driver U1, U4, NFR-001).

## What a future brand pass would change
If a real panchayat name/logo/colour is supplied later (OQ-2), only the header wordmark/logo slot and possibly the single primary accent hue would change — the type scale, spacing, component set, and no-decoration principle should hold, since they are derived from device/performance/literacy drivers, not from branding.
